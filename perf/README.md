# 負荷試験（k6）

## これは何か

**「毎回実行するテスト」ではない。** 単体テスト・E2E は変更のたびに CI で回すが、
負荷試験は**構成やデータ量を変えたときに測り直すもの**である。
CI からは意図的に外してある（1回の実行に数分〜十数分かかり、
結果も実行環境の性能に左右されるため、他の変更を止める根拠にできない）。

見るのは3つ。

| シナリオ | 何を知るためのものか | 閾値 |
|---|---|---|
| `load` | **想定ピーク（50 req/s）を満たせるか** | p95 < 300ms / エラー率 < 1% |
| `stress` | **どこから壊れるか**。上げ切るのが目的で、遅くなること自体は想定内 | エラー率 < 5%（応答時間では落とさない） |
| `spike` | **急に増えても落ちないか**、山を越えたあと元に戻るか | p95 < 3000ms / エラー率 < 5% |

`smoke` はシナリオが通ることの確認用で、**測定ではない**。

閾値の出どころは `docs/requirements.md` 4.5（想定ピーク 50 req/s、読み取り p95 < 300ms）。
**p95 で見るのは、平均が少数の極端に遅い応答に引きずられず「ほとんどの人にとっては速い」
ように見えてしまうため**である。p99 まで求めると外れ値1件で落ちる基準になる。

## 準備

```bash
# k6（v1 以降。TypeScript をそのまま実行できる）
winget install k6 --source winget     # Windows
brew install k6                       # macOS

# 対象を起動しておく
docker compose up -d
docker compose run --rm migrate up
```

## 実行

```bash
node perf/run.mjs smoke     # 1分未満。通ることの確認
node perf/run.mjs load      # 約4分
node perf/run.mjs stress    # 約4分30秒
node perf/run.mjs spike     # 約3分
```

`run.mjs` が **種データの投入 → k6 の実行 → 後片付け**まで行う。

- 種データは既定で **利用者10人 / 投稿2000件**。
  `PERF_USERS_COUNT` と `PERF_POSTS_PER_USER` で変えられる
- 対象は `PERF_BASE_URL`（既定 `http://localhost:8080`）

### 最後まで回すこと

**短い実行だけで済ませない。** `smoke` が通ることは、負荷に耐えることの
根拠にならない。時間がかかるからと `load` を短縮すると、
**段階的に上げている意味（立ち上がりが遅いだけなのか、その負荷に
耐えられないのか）が失われる**。

## 後片付け

**自動である。** 失敗しても、閾値を割っても、`run.mjs` は最後に必ず消す
（レポートは書き出したあとに消すので、結果は残る）。

消す対象は **`perf_` が付いたものだけ**。印で絞らずに消すと、
同じデータベースにある開発用のデータまで巻き込む。

手で確かめるなら:

```bash
docker compose exec -T mysql sh -c 'mysql -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" "$MYSQL_DATABASE" \
  -e "SELECT COUNT(*) FROM users WHERE handle LIKE \"perf\\_%\";"'
```

## レポートの読み方

実行のたびに `perf/results/<シナリオ>-<日時>.json` が出る（Git には入れない）。
端末には k6 の要約が出る。見るところは4つ。

1. **`http_req_duration` の p(95)** — 閾値との比較。ここが本題
2. **`http_req_failed`** — 遅いのか、壊れているのか。遅いだけなら容量の話、
   エラーが出ているなら別の原因がある
3. **`name` タグごとの内訳** — どの操作が遅いのか。
   一覧・検索・制覇マップは負荷のかかり方が違うので分けて記録している
4. **時系列**（`spike` では特に）— 山を越えたあとに元の応答時間へ戻るか。
   戻らないなら、詰まりを引きずっている

閾値を割ったときは、**k6 の数字だけで結論を出さない。**
同時に `docker compose logs backend` と MySQL の状態（接続数・
`SHOW ENGINE INNODB STATUS`）を見ないと、詰まっているのが
アプリケーションなのか、接続プールなのか、索引なのかが分からない。

## 測った結果（2026-08-29、ローカル）

**条件**: Windows 11 / docker compose（MySQL 8.4・Go の API）/ 利用者10人・投稿2000件。
k6 は同じ機械から流している（ネットワークの遅延は入っていない）。

| シナリオ | 最大VU | リクエスト数 | スループット | p95 | エラー率 | 閾値 |
|---|---|---|---|---|---|---|
| `load` | 50 | 76,714 | 316 req/s | **7.9ms** | 0% | 通過 |
| `stress` | 300 | 332,839 | 1,224 req/s | **136ms** | 0% | 通過 |
| `spike` | 200 | 100,257 | 580 req/s | **16.0ms** | 0% | 通過 |

**分かったこと**

- 要件の p95 < 300ms は、想定ピーク（50 req/s）に対して大きく余裕がある
- **限界は見つからなかった。** 300VU まで上げてもエラーは1件も出ず、
  p95 が 7.9ms → 136ms へ伸びただけである（**壊れずに遅くなった**）。
  どこで壊れるかを知るには、さらに上げるか本番相当の構成で測る必要がある
- 急増（10秒で 10VU → 200VU）でも p95 は 16ms に収まり、
  山を越えたあとも引きずっていない

**この数字をどう扱うか**

**本番の予測には使えない。** 本番は ECS Fargate 0.5vCPU×2 / RDS db.t4g.small であり、
この機械より性能が低い。加えて CloudFront・ALB・ネットワークの遅延が入る。
**使えるのは「同じ環境で、変更の前後を比べる」場合だけ**である。

AWS へ載せたら、同じシナリオで測り直して数字を差し替える。

## 測った結果（2026-08-31、AWS）

**条件**: CloudFront → ALB → Fargate 0.5vCPU×1 / RDS db.t4g.small。
k6 は手元の Windows から流している（**通信の遅延が入る**）。
利用者10人・**投稿の種データ無し**（下記「測っていないもの」を参照）。

| シナリオ | 最大VU | リクエスト数 | スループット | p95 | エラー率 | 閾値 |
|---|---|---|---|---|---|---|
| `smoke` | 1 | 70 | 5.7 req/s | 1.11s | 0% | **p95 未達**（下記） |
| `load` | 50 | 59,025 | **234.7 req/s** | **89.5ms** | 0% | 通過 |
| `stress` | 300 | 85,856 | **304.9 req/s** | 1.27s | 0% | 通過 |
| `spike` | 200 | 31,405 | 172.2 req/s | 918ms | 0% | 通過 |

**前回（2026-08-30）との比較**

| | 前回 | 今回 |
|---|---|---|
| `load` スループット | 204.8 req/s | **234.7 req/s** |
| `load` p95 | 108.9ms | **89.5ms** |

静的監査の対応（定期掃除の追加・CSP・タグ付け）で**遅くなっていない。**

### 飽和したのは Fargate の CPU

```
ECS CPU : 99.8%  ← 張り付いている
RDS CPU : 27.2%  ← 余裕がある
```

**限界はデータベースではない。** 増やすならタスク数か vCPU である。
前回（99.2% 対 16.2%）と同じ傾向。

### smoke の p95 が 1.11 秒だった理由

**ログインの bcrypt だった。** 経路ごとに測って切り分けた。

| 経路 | 所要 |
|---|---|
| GET 全般（フィード・検索・通知・都道府県） | 50〜80ms |
| いいね PUT / DELETE | 56〜79ms |
| **ログイン** | **1105〜1145ms** |

`smoke` は 1VU で全経路を1回ずつ叩くため、ログイン1回の重みが p95 に直接出る。
`load`（50VU）では読み取りが大半を占めるため 89.5ms に収まっていた。

**当初は「CloudFront のキャッシュミスや接続確立」だと考えたが、外れていた。**
推測のまま進めていたら見つからなかった。

bcrypt のコストを 12 → 10（ライブラリ既定）に下げた。
要件の p95 < 300ms を満たすのは 10 だけである。詳細は
`backend/internal/auth/secret.go` のコメント。

## 測っていないもの（正直に書いておく）

- **投稿の作成**。画像の処理は S3 のイベントで動く別プロセスであり、
  API の応答時間にその待ち時間は含まれない。ここで測っても意味のある数字にならない
- **画像の配信**。CloudFront から出るため、この構成（ローカル）では測れない
- **本番相当の環境**。ローカルの docker compose は本番（ECS Fargate 0.5vCPU ×2 /
  RDS db.t4g.small）とは性能が違う。**ここで出た数字はそのまま本番の予測にならない。**
  比較に使えるのは「同じ環境で、変更の前後を比べる」場合である
