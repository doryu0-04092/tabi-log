# 運用設計

> **状態: 骨子のみ。** 閾値と障害対応フローは、AWS へデプロイして実測してから確定する。
> 実測なしに決めた閾値は根拠を持たないためである。

## ログ

| 項目 | 方針 |
|---|---|
| 形式 | 構造化 JSON（Go 標準の `log/slog`） |
| 出力先 | **標準出力のみ。ファイルには書かない** |
| 収集 | awslogs ドライバ → CloudWatch Logs |
| レベル | ローカルは debug、コンテナ実行時は info |

**出力先を標準出力に限るのは、アプリケーションがログの送り先を知らない状態を保つためである。**
収集先を変えてもアプリケーションを変更せずに済む（12-factor）。収集はコンテナ基盤の責任として分離する。

### リクエスト追跡

全ミドルウェアの最外周でリクエストごとに ID を発行し、`context.Context` で伝播させる。
レスポンスヘッダー `X-Request-Id` でも返す。

**アクセスログに出すのはメソッド・パス・ステータス・所要時間・追跡 ID のみとする。**
ヘッダー・Cookie・ボディ・クエリ文字列は**構造的にログ出力の経路へ渡さない**。
マスキング方式は書き漏らしで秘密が漏れるため、
認証トークンやパスワードがログに入る経路自体を作らない。

## メトリクス

**CloudWatch EMF（Embedded Metric Format）で構造化ログに埋め込む。**
規定の形式で出力するだけでメトリクスとして扱われるため、
収集エージェントもサイドカーも追加しない。
Fargate + CloudWatch Logs の構成では、この方法が最も部品が少ない。

### 監視項目

| 指標 | 見る理由 |
|---|---|
| リクエスト数 | 負荷の推移 |
| エラー率（5xx） | 障害の検知 |
| p95 レイテンシ | 体感の劣化 |
| DB 接続プール使用率 | 枯渇の予兆。上限に張り付くと待ちが発生する |
| RDS の CPU 使用率 | **スケール判断の主指標**（アプリ側の CPU ではない） |
| ECS の実行タスク数 | 意図せぬ置き換えの検知 |

閾値は**デプロイして実測してから定める**。

## アラート

CloudWatch Alarms → **Amazon SNS** で通知する。

> Amazon SNS は Amazon SES とは別のサービスである。
> 「メール送信機能は実装しない」という方針はアプリケーションの機能に関するものであり、
> 運用のアラート通知とは別の話として扱う。

## 障害対応

デプロイ後に、実際に起きた事象をもとに追記する。現時点で想定しているものだけ挙げる。

| 事象 | 影響 | 一次対応 |
|---|---|---|
| RDS が応答しない | 全 API が失敗。**ただし `/api/livez` は 200 のままなのでタスクは置き換わらない** | RDS のメトリクスを確認。接続数枯渇なら原因のクエリを特定する |
| 画像処理 Lambda が失敗し続ける | 新規投稿ができない（`processed` にならないため）。**既存の投稿と閲覧には影響しない** | Lambda のログを確認。失敗した `media` は `failed` として残る |
| S3 / CloudFront の障害 | 画像が表示されない。**投稿本文は表示される** | 状況を確認し復旧を待つ |
| デプロイ後に 5xx が増える | ECS の circuit breaker が自動でロールバックする | ロールバック後にログを確認 |
