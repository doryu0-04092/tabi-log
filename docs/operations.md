# 運用設計

この文書は「動かし続けるために何を見て、何が起きたらどう動くか」を決めるものである。

> **数値の状態を先に断っておく。**
> ここに書いた閾値のうち、**応答時間だけは実測に基づく**（`perf/` の負荷試験、
> 2026-08-29、ローカルの docker compose）。それ以外の資源の閾値（CPU・接続数・
> ディスク）は **AWS へ載せて実測してから確定する**。実測なしに決めた閾値は
> 根拠を持たず、鳴っても無視されるようになる。暫定であることを都度明記する。

## 1. ログ

### 1.1 形式と送り先

| 項目 | 方針 |
|---|---|
| 形式 | 構造化 JSON（Go 標準の `log/slog`） |
| 出力先 | **標準出力のみ。ファイルには書かない** |
| 収集 | awslogs ドライバ → CloudWatch Logs |
| レベル | ローカルは `debug`、コンテナ実行時は `info`（環境変数 `LOG_LEVEL`） |

**出力先を標準出力に限るのは、アプリケーションがログの送り先を知らない状態を保つためである。**
収集先を変えてもアプリケーションを変更せずに済む（12-factor）。収集はコンテナ基盤の責任として分離する。

### 1.2 レベルの使い分け

**「何が起きたか」ではなく「誰が何をすべきか」で分ける。**
レベルを事象の大きさで決めると、読む側は結局すべてを読むことになる。

| レベル | 意味 | 誰が何をするか | 例 |
|---|---|---|---|
| `ERROR` | **本来起きてはいけないことが起きた** | 人が調べる。アラートの対象 | DB への問い合わせが失敗した / panic を捕捉した / 退会時に S3 の削除に失敗した |
| `WARN` | **想定はしているが、正常ではない** | すぐには動かない。傾向として見る | 失効済みリフレッシュトークンの再提示（盗用の疑い）/ 書き込みの上限で拒否した / `readyz` が DB に到達できない / 画像として処理できなかった |
| `INFO` | **起きたことの記録** | 平時は読まない。追跡のときに辿る | すべての HTTP リクエスト（`http_request`）/ 起動と停止 / 画像を処理した |
| `DEBUG` | **調べるときだけ要る詳細** | 本番では出さない | 認証を断った理由 / 検索の条件の組み立て / **相手が待つのをやめた失敗** |

**`WARN` と `ERROR` の線引き。** 「利用者の操作の結果として起こり得るか」で分ける。
上限に達するのは仕組みが働いた結果であって不具合ではないので `WARN`。
DB に繋がらないのは誰の操作でもないので `ERROR`。

**相手が待つのをやめた失敗は `ERROR` にしない。** 利用者が読み込みの途中で
画面を移ると、データベースの呼び出しが `context.Canceled` を返す。
サーバーは正常なので `DEBUG` に落とし、状態は **499** で返す
（後述）。実際にこれを `ERROR` + 500 にしていたため、
**サーバーが正常なのに壊れて見える**状態を作っていた（2026-08-29 に修正）。

**`DEBUG` を本番で出さない理由。** リクエストごとに複数行増え、
必要な `ERROR` が埋もれる。加えて CloudWatch Logs は取り込み量で課金される。

### 1.3 追跡

全ミドルウェアの最外周でリクエストごとに ID を発行し、`context.Context` で伝播させる。
レスポンスヘッダー `X-Request-Id` でも返す。

**利用者からの問い合わせは、この ID があれば1本に絞り込める。**
無ければ「その時刻あたりの全リクエスト」から探すことになる。

```
fields @timestamp, level, msg, status, duration_ms
| filter request_id = "01JD..."
| sort @timestamp asc
```

### 1.4 ログに含めてはいけない情報

**マスキングでは守らない。渡さない。** マスキング方式は、書き漏らした1か所で漏れる。

| 出さないもの | 理由 |
|---|---|
| パスワード、そのハッシュ | 言うまでもない |
| アクセストークン、リフレッシュトークン、その一部 | **有効なものが載れば、ログを読める人がなりすませる** |
| Cookie、`Authorization` ヘッダー | 上と同じものが入る |
| メールアドレス | 本人を特定できる。利用者 ID で足りる |
| リクエストボディ、クエリ文字列 | 投稿本文・検索語が入る。**何を書いたか・何を探したかは本人のもの** |
| 画像そのもの、S3 の署名付き URL | URL は署名を含み、期限内なら誰でも読める |

**実装での担保。** アクセスログに出すのは
メソッド・パス・ステータス・所要時間・追跡 ID **だけ**である。
ヘッダー・Cookie・ボディ・クエリ文字列は**構造的にログ出力の経路へ渡していない**
（`WithAccessLog` が受け取らない）。

検索のログも、**語そのものは残さず語数だけを残す**。
0件だったときに条件の組み立てを疑える最小限にしてある。

## 2. メトリクス

**CloudWatch EMF（Embedded Metric Format）で構造化ログに埋め込む。**
規定の形式でログに書くだけでメトリクスになり、エージェントもサイドカーも要らない。
Fargate + CloudWatch Logs の構成では、OpenTelemetry Collector を足すより軽い。

> **状態: 未実装。** AWS へ載せる作業とあわせて入れる。
> 現時点で取れているのはアクセスログ（`http_request`）のみで、
> そこから CloudWatch Logs Insights で集計はできる。

### 2.1 監視項目

| 項目 | 出どころ | 何が分かるか |
|---|---|---|
| リクエスト数 | アクセスログ | 使われ方の変化。急増はスパイクか攻撃 |
| エラー率（5xx / 全体） | アクセスログ | **壊れているか**。最優先で見る |
| 4xx 率 | アクセスログ | 画面と API の食い違い。429 の増加は上限が厳しすぎる兆候 |
| **499 の数** | アクセスログ | **相手が待つのをやめた数。** 増えていれば「遅くて待たれていない」ことを示す。エラー率とは分けて見る |
| p95 レイテンシ（経路別） | アクセスログ | **遅くなっているか**。経路別に見ないと原因が絞れない |
| DB 接続プール使用率 | `sql.DBStats` | 詰まりの前兆。100% が続けば待ち行列ができている |
| RDS CPU / 接続数 | CloudWatch（RDS） | DB 側の限界 |
| 画像処理 Lambda のエラー率 | CloudWatch（Lambda） | 新規投稿ができない状態 |
| `media.status='pending'` の滞留数 | 定期クエリ | 孤児オブジェクトの兆候 |

## 3. アラート設計

CloudWatch Alarms → **Amazon SNS** で通知する。

> Amazon SNS は Amazon SES とは別のサービスである。
> 「メール送信機能は実装しない」という方針はアプリケーションの機能に関するものであり、
> 運用のアラート通知とは別の話として扱う。

### 3.1 重大度

**鳴らす基準は「今すぐ人が動くか」で決める。**
動かないものを鳴らすと、鳴っても見なくなる。

| 重大度 | 意味 | 通知 | 対応 |
|---|---|---|---|
| **P1** | **利用者が使えない** | 即時通知 | すぐ対応する |
| **P2** | 一部が使えない / 悪化が続いている | 即時通知 | その日のうちに対応する |
| **P3** | 傾向として気になる | 通知しない（日次で見る） | 次の作業に積む |

### 3.2 鳴らす条件

| # | 条件 | 重大度 | この線にした理由 |
|---|---|---|---|
| A1 | ALB のターゲットが 0 healthy、2分継続 | P1 | 誰も使えない |
| A2 | 5xx 率 > 5%、5分継続 | P1 | 20人に1人が失敗している。単発の失敗と区別するため5分見る。**499 は数えない**（相手が切っただけで、サーバーは失敗していない） |
| A3 | `readyz` の失敗が3分継続 | P1 | DB へ到達できていない。**`livez` は 200 のままなのでタスクは置き換わらない** |
| A4 | p95 > 1000ms、10分継続 | P2 | 要件は 300ms。**AWS の実測は p95 89.5ms**（2026-08-31、load 50VU、`perf/README.md`）なので、1000ms は明らかな異常の線 |
| A5 | 画像処理 Lambda のエラー率 > 10%、10分継続 | P2 | 新規投稿ができない。既存の閲覧には影響しない |
| A6 | DB 接続プール使用率 > 90%、10分継続 | P2 | 詰まる前に気づくための線（暫定・要実測） |
| A7 | RDS の空きストレージ < 20% | P2 | 尽きると停止する。余裕をもって気づく |
| A8 | 429（上限）の発生数が前週比で急増 | P3 | 攻撃か、上限が厳しすぎるか。**どちらもログに残している**（§1.2） |
| A9 | 失効済みリフレッシュトークンの再提示が増加 | P3 | 盗用の兆候。1件では判断できない（並行リフレッシュでも起こり得る） |
| A10 | 499 の割合が普段より大きく増加 | P3 | **遅くて待たれていない兆候。** p95 が閾値に届く前に出ることがある |

**鳴らさないもの**: 単発の 5xx、単発の Lambda 失敗、1回の `readyz` 失敗。
**一時的な失敗で鳴らすと、鳴っても見なくなる。**

### 3.3 通知先の設定

**アラームを作っただけでは、鳴っても誰にも届かない。** 送り先を決めるまで
「監視しているつもり」になる。ここを最後の1手順として明示しておく。

送り先は Terraform の変数 `alert_email` で渡す。**空のままだと SNS の
トピックも購読も作られない**（`infra/lambda.tf`）。アラーム自体は作られるので、
鳴っている事実はコンソールと API からは見える。

```
# infra/terraform.tfvars（.gitignore 済み。公開リポジトリには載らない）
alert_email = "you@example.com"
```

```
cd infra
terraform apply
```

**apply したあと、AWS から購読の確認メールが届く。承認するまで通知は来ない。**
承認を忘れると、設定した本人が「設定した」と思ったまま届かない状態になる。
apply したらメールを確認すること。

確認のしかた:

```
aws sns list-subscriptions-by-topic \
  --topic-arn "$(aws sns list-topics --query "Topics[?contains(TopicArn,'tabilog-alerts')].TopicArn" --output text)" \
  --query 'Subscriptions[].{endpoint:Endpoint,arn:SubscriptionArn}'
```

`SubscriptionArn` が `PendingConfirmation` のままなら、まだ承認されていない。

**メールアドレスをリポジトリに書かないこと。** `infra/terraform.tfvars` は
`.gitignore` 済みで、`terraform.tfvars.example` には差し替え用の値だけ置いてある。

## 4. 障害対応フロー

```
検知 → 状況を1行で書く → 一次対応（止血）→ 原因を調べる → 復旧 → 記録
```

**順番に意味がある。** 原因を調べるより先に止血する。
原因の特定を待つ間、利用者は使えないままである。

### 4.1 検知したら最初にやること

1. **影響を1行で書く。**「誰が」「何ができないか」。
   （例:「全利用者が投稿を開けない。一覧は出る」）
   これを飛ばすと、直したあとに何が直ったのか分からなくなる
2. **時刻を控える。** 始まりが分からないと、直前の変更と結び付けられない
3. **直前のデプロイを確認する。** 障害の多くは変更の直後に起きる

### 4.2 一次対応（止血）

| 状況 | まずやること |
|---|---|
| **デプロイ直後に 5xx が増えた** | **ロールバックする。** ECS の circuit breaker が自動で戻すが、戻り切らなければ手で前のタスク定義に戻す。原因はそのあとで調べる |
| **特定の経路だけ遅い / 落ちる** | その経路の直近の変更を疑う。全体を止めない |
| **DB へ繋がらない** | RDS のメトリクス（CPU・接続数・ストレージ）を見る。接続数の枯渇なら原因のクエリを特定する。**タスクの再起動を先にしない**（DB は回復しない） |
| **原因が分からず全体が使えない** | 直前の変更を戻す。**分からないまま探し続けない** |

### 4.3 想定している事象

| 事象 | 影響 | 一次対応 |
|---|---|---|
| RDS が応答しない | 全 API が失敗。**ただし `/api/livez` は 200 のままなのでタスクは置き換わらない** | RDS のメトリクスを確認。接続数枯渇なら原因のクエリを特定する |
| 画像処理 Lambda が失敗し続ける | 新規投稿ができない（`processed` にならないため）。**既存の投稿と閲覧には影響しない** | Lambda のログを確認。失敗した `media` は `failed` として残る |
| S3 / CloudFront の障害 | 画像が表示されない。**投稿本文は表示される** | 状況を確認し復旧を待つ |
| デプロイ後に 5xx が増える | ECS の circuit breaker が自動でロールバックする | ロールバック後にログを確認 |
| 一覧が急に遅くなった | 全体が遅い | **索引の使われ方を疑う。** 先頭の列が同じ索引が増えると、並べ替えを解決できない側が選ばれることがある（実際に4か所で起きている。`internal/store/query_plan_test.go`） |
| 429 が急増 | 一部の利用者が投稿・コメントできない | ログの `kind` と `user_id` を見る。特定の利用者に偏っていなければ**上限が厳しすぎる**（設定で緩める） |

### 4.4 状態コードの読み方

| 状態 | 意味 | 人が動くか |
|---|---|---|
| 5xx | **サーバーが失敗した** | 動く |
| **499** | **相手が待つのをやめた**（標準の HTTP には無い。nginx の慣習を借りている） | 単発では動かない。**増えていれば遅さを疑う** |
| 429 | 上限で断った | 単発では動かない。偏りを見る |
| 4xx | 要求が通らなかった | 画面と API の食い違いを疑う |

**499 を 5xx に混ぜない。** 混ぜると、利用者が画面を移るだけで
アラートが鳴り、やがて誰も見なくなる。

### 4.5 調べるときの順番

**上から順に、範囲を狭めながら見る。**

1. アクセスログのステータス分布 — **どの経路が失敗しているか**
2. `ERROR` のログ — **何が起きたか**
3. 失敗した1件の `request_id` で全ログを辿る — **どこで止まったか**
4. その時刻の RDS / Lambda のメトリクス — **アプリの問題か、依存先の問題か**

## 5. ポストモーテム（振り返り）

**P1 と P2 は必ず書く。** 書く目的は**同じことを繰り返さないため**であり、
誰の失敗かを決めるためではない。

**人を責めない。** 「なぜ気づかなかったのか」ではなく
「なぜ気づけない作りだったのか」を書く。人に気をつけさせる対策は、
次の担当者には引き継がれない。

`postmortems/YYYY-MM-DD-<短い題>.md` に、次の形で残す。

```markdown
# <何が起きたか（1行）>

## 影響
誰が / いつからいつまで / 何ができなかったか。件数が分かれば書く。

## 時系列
| 時刻 | 起きたこと |
|---|---|
| 10:02 | デプロイ |
| 10:07 | 5xx 率が上がる |
| 10:09 | アラート（A2） |
| 10:14 | ロールバック開始 |
| 10:18 | 復旧 |

## 直接の原因
何がどう壊れたか。**推測と事実を分けて書く。**

## なぜ防げなかったか
- 検知: なぜ気づくのが遅れたか（アラートが無い / 条件が緩い）
- 事前: なぜ出す前に見つからなかったか（テストが無い / 環境が違う）

## やること
| # | 内容 | いつ |
|---|---|---|
| 1 | （**仕組みで防ぐもの**を書く。「気をつける」は書かない） | |
```

**「テストを足す」で終わらせない。** どのテストが、何を検出できていれば
防げたのかまで書く。実際、この案件では
「実 SQL を流すテストが無かったため、カウンタのずれと索引の効き方を
実環境で叩くまで見つけられなかった」という形の抜けが複数あった。

## 6. ダッシュボード

CloudWatch Dashboard を **Terraform で定義する**（手作業で作らない）。
手で作ると、環境を作り直したときに失われ、内容も記録に残らない。

並べるもの（上から）:

1. エラー率と 5xx 数（**まず「壊れているか」**）
2. p95 レイテンシ（経路別）
3. リクエスト数
4. DB 接続プール使用率 / RDS CPU
5. 画像処理 Lambda の実行数とエラー数
