# デプロイ中にしか確認できないこと

## これは何か

**環境が上がっている間にしか確認できない項目の一覧。**

AWS 上の環境は使うたびに作って壊す運用なので、上がっている時間が確認の機会の
すべてになる。ここを取りこぼすと、**次の機会まで未検証のまま残り、
確認のためだけにもう一度課金することになる。**

2026-08-30 のデプロイでは、実際に2件を取りこぼした（後述の「取りこぼした経緯」）。
その再発防止としてこの一覧を置く。

## 使い方

1. **apply の前に、この一覧を上から読む。** 「デプロイでしか検証できないもの」を
   先に用意しておく必要があるためである（CD がこれに当たる）
2. apply 後、**上から順に潰す**
3. **設定を変えてしまう項目は、変える前に済ませる**（レート制限が該当）
4. すべて済ませてから destroy する

---

## 0. apply の前に用意しておくもの

**ここを飛ばすと、環境を上げてからでは間に合わない。**

| # | 用意するもの | 理由 |
|---|---|---|
| 0-1 | **CD ワークフローと IAM** | デプロイでしか検証できない。後から書くと、そのためだけにもう一度 apply することになる |
| 0-2 | 検証用の画像（EXIF 付き） | `node docker/make-exif-fixture.mjs <出力先>` で作る。**入っていることを確かめてから使う**（スクリプトが自分で判定して落ちる） |
| 0-3 | 種データを VPC 内から入れる手段 | `perf/run.mjs` は `docker compose exec mysql` を使うため **AWS には使えない**。索引や全文検索の性能を測るなら先に用意する |

---

## 1. 既定の設定でしか確認できないこと（**最優先。設定を変える前に**）

計測のために上限を上げると、この経路は二度と踏めなくなる。

| # | 確認すること | 手順 | 期待 |
|---|---|---|---|
| 1-1 | **X-Forwarded-For の段数が正しい** | 左端の XFF だけを変えて、上限（既定10回/5分）を超えるまでログインを試す | **429 が返る**。返らないなら左端を採っており、詐称で制限を回避できる |
| 1-2 | **利用者ごとに別々に数える** | 上限に達した状態で、別の経路（別のネットワーク）から1回ログインする | **通る**。通らないなら全員が1つの鍵に潰れている |
| 1-3 | 書き込みの上限 | 投稿を上限（既定20件/時）を超えて作る | 429 が返る |

> **1-1 と 1-2 は両方見ること。** 片方だけでは「制限が効いている」ことと
> 「正しい単位で効いている」ことを区別できない。

---

## 2. 失敗したときの動き

**成功経路だけ通して終わりにしない。** 壊れ方が想定どおりかは、壊してみないと分からない。

| # | 確認すること | 手順 | 期待 |
|---|---|---|---|
| 2-1 | 画像処理が失敗したとき | 画像でないファイルを presign した URL へ送る | `status=failed` になり、その画像では投稿できない |
| 2-2 | 権限が無いとき | 他人の画像の状態を見る／他人の投稿を編集する | **403 が JSON で返る**（HTML でない） |
| 2-3 | 存在しないとき | 存在しない ID・経路を叩く | **404 が JSON で返る** |
| 2-4 | データベースが落ちたとき | RDS を停止する | `/api/livez` は 200 のまま、`/api/readyz` が 503 |

> 2-2 と 2-3 は、CloudFront の `custom_error_response` が全ビヘイビアに効いて
> **API のエラーまで 200 + HTML に化ける**という不具合を実際に踏んだ箇所である。

## 3. 画像の配信

| # | 確認すること | 期待 |
|---|---|---|
| 3-1 | EXIF の GPS が除去される | アップロード前は GPS あり、配信されるものは **Exif ごと無い** |
| 3-2 | リサイズされる | `medium` が 1080 幅に縮む |
| 3-3 | 署名付き Cookie が無いと読めない | **403**（HTML でないこと） |
| 3-4 | 原本に到達できない | `originals/` が **403** |
| 3-5 | キャッシュが効く | 同じ画像を数回取得して `x-cache: Hit` |

## 4. CD

**一度も実行していない場合、ここが最大の未検証項目になる。**

| # | 確認すること | 期待 |
|---|---|---|
| 4-1 | Variables を登録する | `AWS_DEPLOY_ROLE_ARN` / `AWS_STATIC_BUCKET` / `AWS_CLOUDFRONT_DISTRIBUTION_ID` / `AWS_APP_URL` |
| 4-2 | `gh workflow run Deploy` が通る | 全ステップ成功 |
| 4-3 | **IAM の権限が過不足ない** | 特に `ecs:RunTask`・`iam:PassRole`・CloudWatch Logs の読み取り |
| 4-4 | マイグレーションが流れる | `run_migrations=true` で終了コード 0、ログが出る |
| 4-5 | イメージのタグ | `latest` とコミット SHA の2つ |
| 4-6 | タスク定義の引き継ぎ | 環境変数・秘密・CPU/メモリが保たれ、イメージだけ変わる |

## 5. 性能

**種データを入れられるかで、測れる範囲が変わる。**

| # | 確認すること | 前提 |
|---|---|---|
| 5-1 | 想定ピークを満たすか（`load`） | 種データ不要 |
| 5-2 | どこが飽和するか（`stress`） | 種データ不要。ECS CPU と RDS CPU のどちらが先に張り付くかを CloudWatch で見る |
| 5-3 | **索引と全文検索の効き** | **種データが要る**（0-3） |
| 5-4 | 時間経過での劣化（`soak`） | 30分かかる |

## 6. 撤収

| # | 確認すること |
|---|---|
| 6-1 | `terraform destroy` が**中身のあるバケットごと**通る |
| 6-2 | 課金対象が 0 件（RDS / ALB / NAT / EC2 / ElastiCache / EIP / EBS / スナップショット / S3 / ECR / ロググループ） |
| 6-3 | 残るのは ECS タスク定義だけ（**課金ゼロ**） |

## 取りこぼした経緯（2026-08-30）

同じ失敗を繰り返さないために記録しておく。

**① 直した欠陥を、実環境で確認しないまま終えた。**

レート制限が `X-Forwarded-For` の左端を採っており、詐称で無効化できる状態だった。
修正してデプロイしたが、**その直後に負荷計測のため上限を引き上げてしまい、
「直ったこと」を一度も確認しないまま destroy した。**
単体テストは通っているが、実際のヘッダーで確かめてはいない。

→ **1章を最優先に置いた理由がこれである。**

**② CD をデプロイ後に書いた。**

CD は「デプロイでしか検証できないもの」なのに、環境を壊してから着手した。
sns-application では先に用意していたため1回のデプロイで検証まで済んでいる。

→ **0章を置いた理由がこれである。**
