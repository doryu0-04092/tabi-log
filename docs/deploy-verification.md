# デプロイ中にしか確認できないこと

## これは何か

**環境が上がっている間にしか確認できない項目の一覧。**

AWS 上の環境は使うたびに作って壊す運用なので、上がっている時間が確認の機会の
すべてになる。ここを取りこぼすと、**次の機会まで未検証のまま残り、
確認のためだけにもう一度課金することになる。**

2026-08-30 のデプロイでは、実際に2件を取りこぼした（後述の「取りこぼした経緯」）。
その再発防止としてこの一覧を置く。

## 使い方

1. **apply の前に、この一覧を上から読む。** 「デプロイでしか検証できないもの」を
   先に用意しておく必要があるためである（CD がこれに当たる）
2. apply 後、**上から順に潰す**
3. **設定を変えてしまう項目は、変える前に済ませる**（レート制限が該当）
4. すべて済ませてから destroy する

---

## 0. apply の前に用意しておくもの

**ここを飛ばすと、環境を上げてからでは間に合わない。**

| # | 用意するもの | 理由 |
|---|---|---|
| 0-1 | **CD ワークフローと IAM** | デプロイでしか検証できない。後から書くと、そのためだけにもう一度 apply することになる |
| 0-2 | 検証用の画像（EXIF 付き） | `node docker/make-exif-fixture.mjs <出力先>` で作る。**入っていることを確かめてから使う**（スクリプトが自分で判定して落ちる） |
| 0-3 | 種データを VPC 内から入れる手段 | `perf/run.mjs` は `docker compose exec mysql` を使うため **AWS には使えない**。索引や全文検索の性能を測るなら先に用意する |
| 0-4 | **静的監査を先に回す** | **意図を渡していない別のエージェント**に、リポジトリ全体を読ませる。詳細は下記 |

### 0-4: 監査は apply の「前」に回す

**順番が結果を変える。**

```
悪い: 実装 → デプロイ → 検証 → destroy → 監査 → 「未確認」が残る
良い: 実装 → 監査 → デプロイ → 監査の指摘を実環境で確かめる → destroy
```

2026-08-30 は前者だった。監査が destroy の後に走ったため、
**H2（Lambda 失敗時の挙動）・H3（接続枯渇）・M10（EXPLAIN）が推測のまま残った。**
環境が上がっていれば確かめられたものである（`docs/audit-2026-08-31.md`）。

#### 回し方

| 条件 | 理由 |
|---|---|
| **意図を渡さない** | 実装した本人が読むと「こう作らせたはず」の文脈が働いて見逃す。渡すのは仕様書と現物だけ |
| **リポジトリ全体を対象にする** | **層で切らない。** 今日いちばん重かった H1 は `er-diagram.md`（DB設計）× `s3.tf`（インフラ）× `store/posts.go`（バックエンド）を同時に読んで初めて矛盾が見える。「バックエンドの監査」では見つからない |
| **差分ではなく全体** | H1 の証拠は同じ PR に入っていない。差分だけを頻繁に見る形にすると、手間が増えて見つかるものは減る |

#### 判定を必ず残す

**これが無いと 2〜3 回で崩壊する。**

学習用として意図的に割り切った項目（TLS の下限・DB 接続の平文など）は、
**毎回そのまま報告される。** 判定を残さないと、報告そのものが読まれなくなる
（`docs/operations.md`「対応不要のアラートが鳴り続ける状態が最も危険」と同じ形）。

各指摘に次のいずれかを付け、監査記録に残す。

| 判定 | 意味 |
|---|---|
| **直す** | 対応する。PR 番号を書く |
| **割り切る** | 直さないと決めた。**理由を書く。** 次回はこの判定ごと提示する |
| **保留** | 判断できない。**何が分かれば決まるか**を書く |

**「未判定」のまま次回に持ち越さない。** 持ち越した瞬間、一覧は「読まなくてよいもの」になる。

#### あわせて「規定を守れているか」も見る

成果物を読めば判定できる点で静的監査と同じ性質なので、**同じ節目に相乗りさせる。**

`agent-kit` の規定に対して、実際の履歴・コード・文書が外れていないかを確認する。

| 例 | 確かめ方 |
|---|---|
| 実装と検証を別のエージェントに分けたか | 履歴に検証を回した記録があるか |
| 既存資産の更新で CI を通したか | PR の CI が緑か |
| 版を上げる前に必要性を確かめたか | 判断の記録があるか |
| 変更と同じ PR で文書を直したか | 実装の変更に対応する文書の差分があるか |

**見つかった不一致は 2 方向に分ける。**

| 原因 | 対応 |
|---|---|
| 守るべきなのに守らなかった | **是正する** |
| **規定が現実に合っていない** | **規定を直す** |

> 2026-08-31 に「実装と検証は別のエージェントに分ける」という規定があるのに
> **一度も回っていなかった**ことが分かった。原因は規定ではなく**回す契機**が
> 工程に無かったことだった。**この確認は、規定そのものの妥当性検査でもある。**

> **限界も承知しておく。** この確認は**規定に書いてあることしか見ない。**
> 新種の失敗は見つからない。それは節目の振り返りで人が問う
> （`agent-kit/log/decisions/2026-08-31-監査は方向性ではなく規定順守を見る.md`）。

## 0-A. apply の直後にやること（**apply だけではアプリは動かない**）

terraform が作るのは器だけである。**ECR は空、S3 も空、スキーマも無い。**
この状態の ECS サービスはイメージを取得できず、タスクが起動しては落ちるのを
繰り返す。**異常ではなく、まだ中身が無いだけである。**

```
bash docker/bootstrap-deploy.sh
```

**PowerShell から実行するときは Git Bash を明示すること。**
PowerShell の `bash` は WSL の bash に解決される。

```powershell
& "C:\Program Files\Git\bin\bash.exe" docker/bootstrap-deploy.sh
```

**Docker Desktop を起動してから実行すること。** 起動していないと
最初の `docker build` で止まる（スクリプトが先に見て止める）。

| 順 | 何をするか | 飛ばすとどうなるか |
|---|---|---|
| 1 | 画像処理の zip を build | **terraform はビルドしない。** 古い zip がそのまま Lambda に載る |
| 2 | バックエンドのイメージを `initial` で push | ECS が存在しないタグを取りに行き続ける |
| 3 | マイグレーションを流す（`run-migrate.sh`） | **スキーマが無く readyz が通らず、置換が延々と走る** |
| 4 | ECS を強制再デプロイ | push しただけでは切り替わらない。待つと数分かかる |
| 5 | フロントエンドを S3 へ | — |
| 6 | 公開経路で livez / readyz / トップを叩く | **ECS が安定しただけでは経路が通った証拠にならない** |

> **zip が変わったら `terraform apply` が要る。** スクリプトは知らせるだけで、
> apply はしない。2026-08-31 にここを踏んだ — `JWT_SECRET` を環境変数から
> 外したのに、それを不要にするコードが Lambda に届いておらず、画像処理が
> 起動時に落ち続けた。**apply は成功し、plan にも差分は出ない。**
> 気づけるのは画像を1枚上げてみたときだけである（1B-2）。

**順序を変えないこと。** フロントを先に置くと、まだ動かない API を叩く画面が
公開される。

**何度実行してもよい。** 途中で失敗したら直して同じものを流す。

> **ここで止まる理由で多いのは `checkProduction` である**（`audit` L1）。
> 本番の4条件（`COOKIE_SECURE` / `TRUST_PROXY_HEADERS` / `STORAGE_S3_ENDPOINT` /
> `CDN_DOMAIN`）が1つでも欠けると、**意図してアプリを落とす。**
> ログは `aws logs tail /ecs/tabilog --since 10m`。

## 1. 既定の設定でしか確認できないこと（**最優先。設定を変える前に**）

計測のために上限を上げると、この経路は二度と踏めなくなる。

| # | 確認すること | 手順 | 期待 |
|---|---|---|---|
| 1-1 | **X-Forwarded-For の段数が正しい** | 左端の XFF だけを変えて、上限（既定10回/5分）を超えるまでログインを試す | **429 が返る**。返らないなら左端を採っており、詐称で制限を回避できる |
| 1-2 | **利用者ごとに別々に数える** | 上限に達した状態で、別の経路（別のネットワーク）から1回ログインする | **通る**。通らないなら全員が1つの鍵に潰れている |
| 1-3 | 書き込みの上限 | 投稿を上限（既定20件/時）を超えて作る | 429 が返る |

> **1-1 と 1-2 は両方見ること。** 片方だけでは「制限が効いている」ことと
> 「正しい単位で効いている」ことを区別できない。

## 1-B. 監査の対応で新しく壊れうるところ（**最優先**）

**どれも「apply が通っても壊れている」種類である。** plan も validate も通る。

| # | 確認すること | 手順 | 期待 | 壊れていたら |
|---|---|---|---|---|
| 1B-1 | **アプリが起動する** | ECS のタスクが RUNNING になる | 起動する | `checkProduction` が本番の4条件を見ている。**1つでも欠けると起動しない**（それが目的） |
| 1B-2 | **画像処理が起動する** | 画像を1枚上げ、変換物ができる | できる | Lambda から `JWT_SECRET` を外した。`LoadFor(RoleImageWorker)` が効いていないと必須のまま落ちる |
| 1B-3 | **画像が送れる** | 画面から画像を上げる | 成功する | CSP の `connect-src` にバケットが入っていないと、ブラウザが PUT を止める。**コンソールにしか出ない** |
| 1B-4 | **画面が表示される** | トップを開く | 崩れない | CSP の `style-src` / `font-src` が足りないと、書体と一部の見た目だけが落ちる |
| 1B-5 | **ログイン・投稿ができる** | 一通り操作する | 通る | CSP の `script-src` が厳しすぎると、**画面が真っ白になる。** 原因はコンソールにしか出ない |
| 1B-6 | セキュリティヘッダーが付く | `curl -sI https://<配信ドメイン>/` | HSTS / X-Content-Type-Options / X-Frame-Options / Referrer-Policy / CSP | 経路ごとに漏れがないか、`/api/livez` と `/variants/...` でも見る |
| 1B-7 | **本番で仕様の画面が出ない** | `/api/docs` を開く | **404** | 出るなら `IsProduction` が渡っていない |
| 1B-8 | 仕様そのものは読める | `/api/openapi.yaml` | 200 | 危険なのは外部スクリプトであって仕様ではない |

> **1B-3 から 1B-5 は CSP を入れたことによる新しい危険である。**
> CSP で止まったものはエラーにならず、**その要素だけが黙って動かない。**
> ブラウザの開発者ツールのコンソールを開いた状態で確認すること。

### 掃除とアラーム（すぐには確認できないもの）

| # | 確認すること | 手順 | 期待 |
|---|---|---|---|
| 1B-9 | 掃除が動いている | 1時間後にログを見る | `期限切れトークンを掃除した` 等が出る（0件なら出ない） |
| 1B-10 | DLQ とアラームがある | `aws sqs list-queues` / `aws cloudwatch describe-alarms` | キュー1本、アラーム2本。**状態は OK か INSUFFICIENT_DATA** |
| 1B-11 | ECR のライフサイクル | `aws ecr get-lifecycle-policy` | 対象が `untagged` と接頭辞 `sha-` の2つ。**`any` が無いこと** |

> **1B-11 を見落とすと `migrate` / `initial` のイメージが消える。**
> 消えるのは11回目のデプロイ以降であり、そのときには原因を忘れている。

## 2. 失敗したときの動き

**成功経路だけ通して終わりにしない。** 壊れ方が想定どおりかは、壊してみないと分からない。

| # | 確認すること | 手順 | 期待 |
|---|---|---|---|
| 2-1 | 画像処理が失敗したとき | 画像でないファイルを presign した URL へ送る | `status=failed` になり、その画像では投稿できない |
| 2-2 | 権限が無いとき | 他人の画像の状態を見る／他人の投稿を編集する | **403 が JSON で返る**（HTML でない） |
| 2-3 | 存在しないとき | 存在しない ID・経路を叩く | **404 が JSON で返る** |
| 2-4 | データベースが落ちたとき | RDS を停止する | `/api/livez` は 200 のまま、`/api/readyz` が 503 |

> 2-2 と 2-3 は、CloudFront の `custom_error_response` が全ビヘイビアに効いて
> **API のエラーまで 200 + HTML に化ける**という不具合を実際に踏んだ箇所である。

## 3-B. 原本の保持印（H1 の確認）

**アプライしないと確認できない。** LocalStack はタグの検証を本番ほど厳密に行わず、
**署名にタグを含めた PUT が通るかは AWS でしか分からない。**

| # | 確認すること | 手順 | 期待 |
|---|---|---|---|
| 3B-1 | タグを付けて送れる | 画面から画像を1枚アップロードする | **成功する**。403 なら `s3:PutObjectTagging` が足りていないか CORS で `x-amz-tagging` を許可し忘れている |
| 3B-2 | 送信直後は pending | `aws s3api get-object-tagging --bucket <images> --key originals/...` | `state=pending` |
| 3B-3 | 確定すると kept になる | その画像で投稿を作り、同じキーをもう一度引く | **`state=kept`**。pending のままなら 7 日後に原本が消える |
| 3B-4 | 投稿しなければ pending のまま | アップロードだけして投稿を作らない | `state=pending` のまま |
| 3B-5 | ライフサイクルの条件 | `aws s3api get-bucket-lifecycle-configuration --bucket <images>` | `And` に `Prefix=originals/` と `Tag state=pending` の両方がある |

> **3B-1 を最初に踏むこと。** ここが落ちると画像を使う確認が全部できない。
> **タグの付け忘れは静かに壊れない**（署名不一致で拒否される）が、
> **kept への変更漏れは静かに壊れる** — 気づくのは 7 日後である。3B-3 は省略しない。

## 5. 性能

**種データを入れられるかで、測れる範囲が変わる。**

### 測る前に上限を上げる（1章を終えてから）

**負荷試験は 1 章と両立しない。** 試験の setup は利用者10人ぶんの
トークンを取るため、**1回の実行でログイン試行の上限をちょうど使い切る。**
シナリオの間隔（4〜4分半）は窓（5分）より短く、2本目以降が必ず 429 になる。

```
terraform apply -var login_attempt_limit=1000   # 測る前
terraform apply                                 # 測り終えたら戻す
```

> **順序を逆にしないこと。** 上げたあとでは 1-1・1-2 を確かめられない。
> 2026-08-31 は 1 章を先に済ませていたため、この順で進められた。

**戻し忘れると、次の環境が緩いまま立ち上がる。**
既定値（10）はアプリケーション側と同じで、変えない限り挙動は変わらない。

| # | 確認すること | 前提 |
|---|---|---|
| 5-1 | 想定ピークを満たすか（`load`） | 種データ不要 |
| 5-2 | どこが飽和するか（`stress`） | 種データ不要。ECS CPU と RDS CPU のどちらが先に張り付くかを CloudWatch で見る |
| 5-3 | **索引と全文検索の効き** | **種データが要る**（0-3） |
| 5-4 | 時間経過での劣化（`soak`） | 30分かかる |

## 取りこぼした経緯（2026-08-30）

同じ失敗を繰り返さないために記録しておく。

**① 直した欠陥を、実環境で確認しないまま終えた。**

レート制限が `X-Forwarded-For` の左端を採っており、詐称で無効化できる状態だった。
修正してデプロイしたが、**その直後に負荷計測のため上限を引き上げてしまい、
「直ったこと」を一度も確認しないまま destroy した。**
単体テストは通っているが、実際のヘッダーで確かめてはいない。

→ **1章を最優先に置いた理由がこれである。**

**② CD をデプロイ後に書いた。**

CD は「デプロイでしか検証できないもの」なのに、環境を壊してから着手した。
sns-application では先に用意していたため1回のデプロイで検証まで済んでいる。

→ **0章を置いた理由がこれである。**
