# 技術スタック

## 選定の前提

このプロジェクトには、通常の技術選定にはない制約が2つある。

1. **直前に作った `sns-application` と同じ技術スタックを使わない。** ポートフォリオとしての重複を避け、新しい領域を学ぶことが目的である
2. **クラウドは AWS に統一する。** ただしどの AWS サービスを使うかは、実装内容に合わせて選び直す

TypeScript のみ例外として継続使用する。

そのため本書には、通常の選定理由に加えて「前回と何を変えたか、なぜ変えたか」を併記する。

### 前回（sns-application）の構成

| 層 | 前回の採用 |
|---|---|
| フロントエンド | React 19 + Vite + TypeScript + TanStack Query + react-router + Tailwind CSS |
| バックエンド | Java 21 + Spring Boot 3.5 + MyBatis + Maven |
| データベース | PostgreSQL 16 + Flyway |
| API 仕様 | springdoc による code-first 生成 |
| インフラ | Terraform / CloudFront + S3 + ALB + ECS Fargate + RDS |

### Vite についての但し書き

Vite は上記のとおり前回使用しており、本来なら除外対象である。
ただし **SvelteKit のビルドは内部で Vite を使う**。これはこちらが選ぶものではなく
フレームワークの内部実装であり、「同じ構成を繰り返さない」という制約の趣旨には反しないため、
除外対象から外して扱う。黙って通すのではなく、判断としてここに記録しておく。

## 全体構成

```
[SvelteKit (SPA)]  ── REST/JSON ──  [Go (net/http)]  ──  [MySQL 8.4]
  :5173 ネイティブ起動                :8080 コンテナ         コンテナ
```

フロントエンド・バックエンド・DB を分離した3層構造とする。前回と同じ層構成だが、
各層の中身をすべて入れ替えている。層構成まで変えなかったのは、**技術の差だけを比較できる形に
しておくため**である（同じ設計で言語とフレームワークだけが違う2つの実装が手元に残る）。

## 選定一覧

### フロントエンド

| 項目 | 採用 | 理由 |
|---|---|---|
| フレームワーク | **SvelteKit 2 + Svelte 5（runes）+ TypeScript** | リアクティビティのモデルが React と根本的に異なる。React は再レンダリングして差分を求めるが、Svelte はコンパイル時に更新箇所を確定させる。同じ設計の画面を両方で作ることで、この差が実感として残る |
| レンダリング | **`adapter-static` ＋ SPA フォールバック** | 配信を CloudFront + S3 の静的配信に保ち、Go の API を唯一のサーバーにするため。3層分離が素直に成立する |
| 状態管理 | **Svelte 5 runes ＋ SvelteKit の `load`** | 追加ライブラリを入れない。前回 TanStack Query が担っていたキャッシュ・再検証の層は、薄い `$lib/api/client.ts` として自前で持つ |
| CSS | **Svelte のスコープ付き CSS ＋ CSS カスタムプロパティ** | Svelte は単一ファイル内の CSS が既定でコンポーネントにスコープされる。Tailwind を外した穴を**依存を1つも増やさずに**埋められる |
| テスト | Vitest（単体）/ Playwright（E2E、axe-core 同梱） | Playwright は既存プロジェクトで運用実績がある |

**この選択の代償を明記する。** `adapter-static` は SSR を行わないため、
**SNS で共有したときの OGP カードが出ない**。旅行写真の共有とは本来相性の良い機能を、
インフラ構成の単純さとコストを優先して落としている。
後から必要になった場合は `adapter-node` に切り替えて Fargate にもう1つコンテナを立てることになり、
**インフラ構成の変更を伴う**。アプリ側だけの変更では済まない。

### バックエンド

| 項目 | 採用 | 理由 |
|---|---|---|
| 言語 | **Go 1.27** | 今回の中核となる新規学習対象。コンパイル型・静的型・軽量な実行イメージという、前回の JVM とは別の運用特性を持つ |
| HTTP | **標準ライブラリの `net/http` ＋ `ServeMux`** | Go 1.22 以降の `ServeMux` は `GET /api/posts/{id}` のようなメソッド付きパターンを扱える。**Echo や Gin は独自の `Context` 型が全ハンドラに侵食するためロックインが強い**のに対し、標準の `http.Handler` に揃えておけばルーターは後から差し替えられる。ミドルウェア（CORS・ログ・リカバリ・リクエストID・レート制限）は自前で書く量が小さく、中身が見える点でも学習に向く |
| DB アクセス | **sqlc**（SQL から型安全な Go コードを生成）＋ `database/sql` ＋ `go-sql-driver/mysql` | 前回 MyBatis を選んだ理由（SQL を自分で書いて理解する）をそのまま引き継ぐ。ORM を挟まない。ただし**動的な検索クエリだけは sqlc の外に出す**（後述） |
| マイグレーション | **golang-migrate**。**起動時の自動適用はしない** | 前回は Flyway がアプリ起動時に適用していた。今回はデプロイとスキーマ変更を切り離し、明示コマンドで適用する |
| バリデーション | `go-playground/validator` | 前回の Bean Validation に相当する宣言的な検証 |
| ログ | **標準の `log/slog`** で構造化 JSON を標準出力へ | 前回は Logback ＋ logstash-logback-encoder を使った。同じ思想（出力先をアプリが知らない／12-factor）を**依存ゼロ**で実現できる |
| リクエスト追跡 | 自前ミドルウェアで UUID を発行し `context.Context` で伝播、`X-Request-Id` で返却 | 前回の MDC に相当。**ヘッダー・Cookie・ボディ・クエリ文字列はログ出力の経路に渡さない**設計を踏襲する（マスキングは消し忘れで漏れるため、経路自体を作らない） |
| AWS SDK | `aws-sdk-go-v2`（S3 のみ） | 前回の S3 設計を Go へ移植する |
| CloudFront の署名 | **標準ライブラリのみ**（`crypto/rsa` + `encoding/base64`） | 署名付き Cookie の形式は RSA-SHA1 と置換 base64 と決まっており、**選択の余地が無い**。SDK の `feature/cloudfront/sign` を足すこともできたが、40行程度のために依存を増やす理由が無いと判断した。**AWS が公開している符号化の例と一致することをテストで固定している** |

### 認証

**アクセストークン ＋ リフレッシュトークンのトークン方式**を採用する。

> これは前回 `sns-application` と同じ認証方式である。「前回のスタックを使わない」という制約の
> 例外として、依頼者の明示的な指定により採用した。実装言語とライブラリは
> Java/jjwt から Go/golang-jwt に変わる。

| | 方式 | 寿命 | 保存場所 |
|---|---|---|---|
| アクセストークン | JWT（HS256、`golang-jwt/jwt/v5`） | 15分 | **JavaScript のメモリのみ。`Authorization` ヘッダで送信し、localStorage には保存しない** |
| リフレッシュトークン | 暗号論的乱数32バイト（opaque）。DB には **SHA-256 ハッシュのみ**保存 | 7日 | **HttpOnly ＋ Secure ＋ SameSite=Strict Cookie、`Path=/api/auth` に限定** |

> **`Path` を `/api/auth/refresh` まで絞らない理由（実装時に判明）**:
> ログアウトでも Cookie を読んでサーバー側で失効させる必要がある。
> `/api/auth/refresh` に限定すると `/api/auth/logout` へ Cookie が送られず、
> ブラウザ側で消すことしかできなくなる（サーバー上のトークンが生き残る）。
> `/api/auth` までとし、投稿や検索といった他の API には乗らない状態は保つ。

前回は両方を Cookie に格納した。今回ヘッダ方式に変えたことで、**CSRF の対象が
Cookie を使う2つのエンドポイント（`/api/auth/refresh`・`/api/auth/logout`）だけに縮小する**。
代わりにアクセストークンは JavaScript が保持することになるため、localStorage を使わず
メモリ保持に限定し、リロード時はリフレッシュで復元する。

#### 鍵の扱い

- クレームは `sub` / `iat` / `exp` / `jti` / `typ="access"`
- **ヘッダに `kid`（鍵ID）を最初から入れる**
- 鍵は「秘密1つ」ではなく **`kid` から {鍵, アルゴリズム} を引くマップ**として設定から読む（現在は1件のみ）
- **検証時に許可アルゴリズムを必ず明示する**（`jwt.WithValidMethods`）

最後の点は必須である。`alg` をトークンの自己申告どおりに信用すると、
HMAC と公開鍵方式が混在した際に **公開鍵を HMAC の共有鍵として使って署名を偽造される**
（alg confusion 攻撃）。公開鍵は秘密ではないため誰でも入手できることが成立の理由である。

この構造にしておくことで、将来 HS256 から EdDSA（Ed25519）へ**無停止で移行できる**。
検証側に新しい鍵を追加 → 発行を切り替え → アクセストークンの寿命（15分）が経過したら旧鍵を削除、
という手順になり、**変更は `internal/auth` パッケージと SSM のパラメータに閉じる**
（DB のマイグレーションもフロントエンドの変更も発生しない）。

**鍵の生成手段も確認済み（2026-08-28）**: Terraform の `tls_private_key` リソースは
`algorithm = "ED25519"` を受け付ける（`terraform plan` で実際に通ることを確認した）。
移行時に鍵を手動生成して投入する必要はない。

#### リフレッシュのローテーションと盗用検知

使用の都度ローテーションし（新規発行＋旧失効）、失効済みトークンが再提示されたら
盗用の兆候とみなしてそのユーザーの全トークンを一括失効する。

**ただし、これを素直に実装すると正常な利用者が突然ログアウトされる。**
タブを2枚開いている場合や、ページ表示時に複数の API 呼び出しが同時に 401 を受けた場合、
両方が同じリフレッシュトークンで更新を試みる。先に処理された方がローテーションするため、
後から来た方は「失効済みトークンの提示」＝盗用と判定されてしまう。

対処として、**旧トークンに後継トークンの ID（`replaced_by`）を保持し、
猶予時間内（10秒）の提示には後継を返す**。それより後の提示のみ盗用と判定する。
フロントエンド側でも、同時に発生した 401 を1本のリフレッシュ処理に束ねて二重に防ぐ。

ローテーションの「旧を失効 → 新を発行」は**必ず同一トランザクションで行う**。
分かれていると、その間にプロセスが停止した場合に強制ログアウトか二重発行が生じる。

#### 割り切り

リフレッシュトークンは DB 上で失効させられるため即座に無効化できるが、
**発行済みのアクセストークンは最大15分間有効なまま**である。
ブラックリストを持てば消せるが、結局リクエストごとに DB を参照することになり
JWT を使う意味が薄れるため採らない。「ログアウト後も最大15分は既存トークンが通る」ことを
仕様上の制約として受け入れる。

### API 仕様 — code-first から spec-first へ

前回は springdoc による code-first だった。この方式で
**「成功レスポンスが存在しない」仕様書が生成される事故**を起こしている
（エラー用に 403 の注釈を追加したところ、自動生成されていた 200 の *改名* と解釈され、
200 が消えた。コンパイルもテストも Swagger UI の描画も通るため、
生成された JSON を目視するまで気づけなかった）。

今回は向きを逆にする。

```
docs/openapi.yaml  ← 人間が書く。これが唯一の正
   ├→ oapi-codegen        → backend/internal/api/gen/     （Go の server interface と型）
   └→ openapi-typescript  → frontend/src/lib/api/gen.ts   （TypeScript の型）
```

CI で**再生成して差分が出ないこと**を検証する。
仕様が正であるため、「実装が仕様と食い違う」ことは型検査の失敗として現れる。

### データベース

| 項目 | 採用 | 理由 |
|---|---|---|
| エンジン | **MySQL 8.4 LTS** | 前回の PostgreSQL に対する入れ替え。**8.0 は 2026年4月に EOL 済みのため採らない**。8.4 は LTS で 2032年までサポートされる |
| 文字セット | `utf8mb4` / `utf8mb4_0900_ai_ci` | 絵文字を含む日本語を正しく扱うため |
| 全文検索 | **InnoDB FULLTEXT ＋ ngram パーサ** | **日本語は空白で区切られないため、既定のパーサでは全文検索が機能しない**。ngram パーサは既定でトークン長2で全文を刻む |
| マイグレーション | golang-migrate（前回は Flyway） | 上記のとおり起動時の自動適用をやめるため |

**RDS での提供状況を確認済み（2026-08-28、`aws rds` API で実測）**

| 確認項目 | 結果 |
|---|---|
| ap-northeast-1 の MySQL 8.4 系 | 8.4.5 〜 8.4.11 が `available`。**既定は 8.4.9** |
| `db.t4g.small` + gp3 | **注文可能**（最小20GB / 最大16TB / VPC / Multi-AZ 対応） |
| `db.t4g.micro` + gp3 | 同様に可能（規模を下げる余地は残っている） |
| `ngram_token_size` | パラメータグループ系列 `mysql8.4` に存在し **変更可能**。許容値 1〜10、**`static`（変更に再起動が必要）** |

Extended Support や Aurora への切り替えは不要である。
`ngram_token_size` が `static` である点は運用上重要で、
**この値を変えるには DB インスタンスの再起動と全文索引の再構築が必要になる。**
ローカルの docker-compose も同じ 2 に固定しており、開発と本番で挙動を揃えている。

### インフラ

Terraform を継続する（インフラは「AWS で同様の形に統一する」という指定のため）。
構成は [AWS構成設計](aws-architecture.md) に詳述する。

前回からの意図的な差分は4点。

| 項目 | 前回 | 今回 | 理由 |
|---|---|---|---|
| Fargate | 0.25 vCPU / 512MB × 1 | **0.5 vCPU / 1GB × 2** | ピーク 50 req/s の想定に対し 0.25 vCPU（1/4コア）では不足する |
| RDS | db.t4g.micro | **db.t4g.small** | 投稿20万件・いいね200万行の規模では、micro のバッファプール（実質600MB程度）にデータと索引が乗り切らない |
| ヘルスチェック | `/api/health`（DB 疎通込み） | **`/api/livez`（DB を見ない）と `/api/readyz`（DB 疎通）に分離** | 前回は RDS が一時的に不調になると全タスクが unhealthy と判定されて一斉に置き換えられる構造だった（前回の文書に未対応課題として記録されている） |
| 画像処理 | なし | **S3 イベント → Lambda（Go）** | EXIF 除去・形式検証・サムネイル生成を行う |

Lambda のランタイムも Go とし、バックエンドと言語を統一する。

## 拡張性を重点に置く2領域

依頼者の指定により、**画像まわりと検索**については拡張しやすさを設計の重点に置く。

### 画像

**`posts` に画像の URL を直接持たせず、`media` テーブルに分離する。**

```
posts 1 ── N media ── N media_variants
```

これにより、複数枚の画像・アバター・将来の動画が同じ構造に乗る。
`posts.image_url` のような列を持つと、複数枚に対応する時点で全面的な作り直しになる。

ストレージは `Storage` インターフェース（`PresignPut` / `SignedURL` / `Delete` の3メソッド）で
切り、実装として S3 と LocalStack を持つ。CloudFront 署名付き Cookie への切り替えも
このインターフェースの裏側に閉じる。

### 検索

`PostSearcher.Search(ctx, keyword, filters, cursor)` の1インターフェースで切り、
初期実装を MySQL とする。フィルタの軸（都道府県 / タグ / ユーザー / 訪問日の期間 / キーワード）は
最初から直交する形で定義し、軸を後から足せるようにする。

**この抽象化には根拠がある。** ngram パーサはトークン長2で全文を刻むため、
本文500文字の投稿20万件で1億件規模のトークンエントリになり、バッファプールを圧迫しうる。
実測の結果によっては OpenSearch への差し替えが現実的な選択肢になるため、
**投機的な抽象化ではなく、起こりうる変更に備えた設計**である。

**動的な検索クエリだけは sqlc の外に出す。** sqlc は静的な SQL からコードを生成する仕組みで、
条件が可変で AND が増減するクエリは扱えない。検索リポジトリのみ `database/sql` で
クエリを組み立てる。その際、値は必ずプレースホルダにバインドし、
ユーザー入力を SQL 文字列に連結しない。

### 拡張性についての但し書き

実装が1つしかない段階での抽象化は投機的になりやすい。
今回は **「インターフェース1枚 ＋ アダプタ1個」までに留め**、
設定駆動のパイプラインやプラグイン機構のような、使われない汎用化は作らない。

一方で `media` テーブルの分離と上記2つのインターフェースは、
**後から入れると全面改修になる種類のもの**であるため、最初から入れる。

## 技術選定の観点

| 観点 | 見た結果 |
|---|---|
| **長期継続性** | Go（Google）・MySQL（Oracle ＋ OSS コミュニティ）・AWS はいずれも問題ない。**SvelteKit には懸念がある** — 中核の開発チームが小規模で、エコシステムは React と比べて明確に小さい。詰まったときに前例が見つかりにくいコストを承知のうえで選ぶ |
| **LTS 優先** | MySQL は 8.4 LTS を採用する（8.0 は EOL 済み）。Node.js は Active LTS 系を CI とローカルで固定する。**Go と Svelte には LTS の概念がない** — Go は各リリースに約1年のセキュリティ修正が入るが、Svelte にはその枠組みがない。**非 LTS を選んでいる点を割り切りとして記録する** |
| **後方互換性** | **Go の Go1 互換性保証が候補中で最も強い**（Go を選んだ主要な根拠のひとつ）。逆に **Svelte は 3→4→5 で破壊的変更の実績があり、runes の導入は特に大きい**。本構成で最も弱い箇所であり、メジャーアップグレード時にフロントエンドの書き換えが必要になる可能性を見込んでおく |
| **移行計画** | 全体としては強い。3層分離しており、API の契約が `docs/openapi.yaml` に固定されているため、**フロントエンドだけを差し替えられる**。Go 側は標準 `net/http` に寄せたのでルーターは剥がせ、sqlc の生成物は素の Go コードである。MySQL から他の RDB への移行は SQL 方言の差に留まる。認証は `internal/auth` に閉じており EdDSA へ無停止移行できる |
