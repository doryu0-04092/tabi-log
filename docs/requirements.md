# 要件定義書

## 1. 目的と背景

旅行先の写真と記録を投稿し、他の利用者と共有する SNS を作る。

汎用の写真 SNS と異なり、投稿には **都道府県**（必須）と **訪問日** を紐づける。
これにより「どこへ、いつ行ったか」が自由テキストではなく構造化データとして残り、
地域での絞り込みや、利用者ごとの旅行履歴の集計（都道府県制覇マップ）が成立する。

スクール課題であり、**学習目的の構成**である。可用性やコストの面で本番運用には
適さない割り切りを複数含む。該当箇所は [AWS構成設計](aws-architecture.md) に列挙する。

## 2. 想定利用者

日本国内を旅行し、その記録を写真とともに残したい個人。
アカウントを持つ利用者のみが閲覧・投稿できる（非ログインでの閲覧は提供しない）。

## 3. スコープ

### 3.1 実装する機能

| 領域 | 機能 |
|---|---|
| アカウント | サインアップ / ログイン / ログアウト / プロフィール表示・編集 / パスワード変更 / 退会 |
| 投稿 | 画像1〜4枚 ＋ 本文 ＋ 都道府県（必須）＋ スポット名 ＋ タグ ＋ 訪問日 / 編集 / 削除 |
| 反応 | いいね・解除 / コメント（フラット1階層）・削除 |
| 関係 | フォロー・解除 / フォロー一覧 / フォロワー一覧 |
| フィード | フォロー中フィード / 新着フィード |
| 発見 | 都道府県で絞り込み / タグで絞り込み / キーワード全文検索 / ユーザー検索 / 人気順 |
| 通知 | いいね・コメント・フォローの通知 / 未読数 / 既読化 |
| 特色 | プロフィールの都道府県制覇マップ（訪問済みの県の塗り分けと制覇率） |

### 3.2 実装しない機能（意図的な対象外）

| 対象外 | 理由 |
|---|---|
| **メール送信** | SES のドメイン検証とサンドボックス解除が学習の本筋から外れるため。結果として**パスワードリセットとメールアドレス確認も提供しない** |
| 投稿の公開範囲設定 | 認可の組み合わせが増え、フィード・検索・通知のすべてに条件が波及する。全投稿はログイン利用者に公開される前提とする |
| ブロック / ミュート | 同上 |
| コメントの返信ツリー | 再帰構造の取得と表示が主題ではないため、1階層のフラットなコメントに限定する |
| ダイレクトメッセージ | 別種のリアルタイム性が必要になるため |
| 多言語対応 | 日本国内の旅行に限定しているため、UI は日本語のみ |
| モバイルアプリ | Web のみ |
| 決済 | 収益機能を持たない |

### 3.3 地理情報の扱い

**日本国内・都道府県レベルに限定する。** 緯度経度は保持せず、地図上の位置表示や
「現在地周辺の投稿」といった地理検索は行わない。

- 都道府県は `prefectures` マスタ47件から**選択**させる（自由入力しない）
- コードは **JIS X 0401**（総務省が定める都道府県コード 01〜47）を採用し、独自採番はしない
- スポット名（「道の駅○○」等）のみ自由記述とする。全文検索の対象には含めるが、絞り込みの軸にはしない

**選択式にする理由**は、自由入力にすると「北海道」「ほっかいどう」「Hokkaido」「北海道 札幌」が
別の値として分散し、**地域での絞り込みという中核機能が事実上成立しなくなる**ためである。

将来の海外対応は `posts` への列追加で対応できる範囲であり、現時点で汎用的な地名テーブルは設けない。

### 3.4 訪問日と投稿日を区別する

旅行から帰ったあとにまとめて投稿するのが自然な使われ方であるため、時間軸を2つ持つ。

| 軸 | 用途 |
|---|---|
| 投稿日（`created_at`） | フィードの並び順 |
| 訪問日（`visited_on`） | プロフィールの旅行履歴の並び順、期間での絞り込み |

## 4. 非機能要件

### 4.1 性能

| 項目 | 目標 |
|---|---|
| 想定利用者数 | 2,000 |
| 想定投稿数 | 200,000 |
| 1利用者あたりのフォロー数 | 平均 200 |
| ピーク時のリクエスト | 50 req/s |
| 一覧系 API の応答 | p95 で 300ms 未満 |

- 索引は**初回のマイグレーションから投入する**。前回プロジェクトでは索引の欠落を性能テストで
  事後に検出しており、同じ手戻りを避ける
- いいね数・コメント数は**カウンタ列として保持**し、本体の更新と同一トランザクションで増減させる。
  フィード20件それぞれに `COUNT` を発行すると N+1 の温床になるため
- 一覧の取得は**カーソルページネーション**とする。`OFFSET` は深いページで劣化するため使わない

### 4.2 可用性

学習用途のため SLA を定めない。RDS は Single-AZ、ECS タスクは2つ。
**デモ後は `terraform destroy` する運用を前提とする。**

### 4.3 セキュリティ

| 項目 | 方針 |
|---|---|
| パスワード | bcrypt でハッシュ化して保存する。平文・可逆暗号では保持しない |
| 認証 | アクセストークン（JWT・15分）＋ リフレッシュトークン（opaque・7日）。詳細は [技術スタック](tech-stack.md) |
| CSRF | アクセストークンは `Authorization` ヘッダで送るため通常 API は非該当。Cookie を用いる `/api/auth/refresh` と `/api/auth/logout` の2本のみ対策する |
| 認可 | 「自分の投稿・コメントのみ編集・削除できる」ことを**サーバー側で必ず検証**する。フロントエンドの制御は UX のためであり、権限の根拠にはしない |
| レート制限 | ログイン試行（IP単位・アカウント単位）、投稿とコメントの作成に上限を設ける |
| 画像アップロード | 署名付き URL に Content-Type と最大サイズを焼き込む。加えてサーバー側でマジックバイトを検証し、拡張子や申告された Content-Type を信用しない |
| ストレージ | S3 バケットはパブリックアクセスを全面的に遮断し、CloudFront の OAC からのみ読み取れるようにする |
| 依存の脆弱性 | `govulncheck`・`npm audit`・Dependabot を CI で継続的に実行する |

### 4.4 プライバシー

**投稿画像の EXIF から GPS 座標・撮影日時・端末情報を必ず除去する。**

地理情報を都道府県レベルに絞る判断をしていても、画像の EXIF に緯度経度が残っていれば
自宅や訪問先がピンポイントで特定されうる。旅行の記録は行動履歴そのものであり、
**画像経由でこの配慮が無効化されることを構造的に防ぐ**必要がある。

除去はサーバー側（S3 イベントで起動する Lambda）で行い、フロントエンドの処理に依存させない。
除去が完了していない画像は投稿として公開できない状態に留める。

その他:

- 退会時の削除方針を [機能一覧](features.md) に明記する
- ログにパスワード・トークン・メールアドレスを出力しない。マスキングではなく、
  **これらをログ出力の経路に構造的に渡さない**設計とする

### 4.5 アクセシビリティ

写真が主役のサービスであるため、代替情報の提供を必須要件とする。

| 項目 | 方針 |
|---|---|
| 画像の代替テキスト | **対象外とする**（2026-08-29 に方針変更）。理由と代償は下記 |
| 都道府県制覇マップ | **地理的な地図ではなく、均一なマスのタイルグリッドを自作する。** 実地図では香川・大阪・東京のタップ領域が数ピクセルになり、県によって操作しやすさが極端に変わるため。色の違いだけで情報を伝えず、同じ内容を表形式でも提供する（[機能一覧](features.md) 8 章） |
| キーボード操作 | モーダルとドロップダウンでフォーカスを閉じ込め、フォーカス位置を可視化する |
| コントラスト比 | 文字と背景で 4.5:1 以上 |
| 機械的な検証 | Svelte のコンパイル時 a11y 警告を CI でエラーとして扱う。加えて Lighthouse CI と axe-core を CI に組み込む |

> **画像の代替テキストを対象外にした（2026-08-29）**
>
> 当初は「写真が主役のサービスで任意にすると実質的に入力されない」という理由で
> 入力を必須にしていた。その後、**投稿のたびに画像ごとの入力を求めるのは負担が
> 大きい**という判断で任意にし、さらに**入力欄そのものを廃止**した。
>
> **代償を明記する。** 画像を見られない利用者（スクリーンリーダーの利用者、
> 画像の読み込みに失敗した環境など）に、写真の内容が一切伝わらなくなる。
> 本文で補われる場合を除き、その投稿は「画像がある」ことしか分からない。
>
> **やっていること**: `img` には空の `alt=""` を出す。属性ごと省くと HTML として
> 不正であり、読み上げがファイル名を読み上げてしまう。`alt=""` は
> 「読み上げる内容が無い」を表す正しい書き方である。
> 写真そのものをリンクにしている箇所には `aria-label` で行き先を持たせ、
> 「リンク」としか読まれない状態は避けている。

### 4.6 可観測性

- ログは構造化 JSON を標準出力にのみ出す。ファイルには書かない
- リクエストごとに ID を発行し、そのリクエスト中の全ログに付与する。`X-Request-Id` として返す
- メトリクスは CloudWatch EMF 形式でログに埋め込む（収集エージェントを追加しない）
- 監視項目: リクエスト数 / エラー率 / p95 レイテンシ / DB 接続プール使用率 / RDS CPU / 5xx 率

### 4.7 保守性

- API 仕様（`docs/openapi.yaml`）を唯一の正とし、サーバーとクライアントの型をそこから生成する
- 生成物は CI で**再生成して差分が出ないこと**を検証する
- 既存資産の更新は CI が緑であることを確認してから完了とする

## 5. 前提と制約

- 対象ブラウザは各モダンブラウザの最新版とする。IE は対象外
- クラウドは AWS に統一する
- 使用言語は Go・TypeScript・SQL とする
