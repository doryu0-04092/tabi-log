# 機能一覧

各機能の受け入れ条件と、実装時に判断が要る点を記す。
「何を作らないか」は [要件定義書](requirements.md) 3.2 にある。

実装の順序は下記の章立てのとおりとする。前の章が動かないと次が検証できない依存関係になっている。

---

## 1. アカウント

### 1.1 サインアップ

| 項目 | 内容 |
|---|---|
| 入力 | メールアドレス / ハンドル / 表示名 / パスワード |
| ハンドル | 英数字とアンダースコアのみ、3〜30文字。**一意**。URL に使う |
| パスワード | 8文字以上。bcrypt でハッシュ化して保存する |
| 成功時 | アクセストークンを返し、リフレッシュトークンを Cookie に設定する |

**受け入れ条件**

- 既に使われているメールアドレス・ハンドルでは登録できない
- パスワードは**平文でもハッシュでも**レスポンスに含まれない
- パスワードとメールアドレスがログに出力されない

> **メールアドレスの確認は行わない。** メール送信を対象外にしているためである
> （[要件定義書](requirements.md) 3.2）。存在しないアドレスでも登録できる。
> 学習用途として許容し、仕様として明示しておく。

### 1.2 ログイン / ログアウト / トークン更新

| エンドポイント | 内容 |
|---|---|
| `POST /auth/login` | メールアドレスとパスワードで認証する |
| `POST /auth/refresh` | リフレッシュトークン（Cookie）から新しいアクセストークンを得る |
| `POST /auth/logout` | リフレッシュトークンを失効させ、Cookie を削除する |

**受け入れ条件**

- 認証失敗時、「メールアドレスが存在しない」と「パスワードが違う」を**区別しない**
  （区別すると、どのアドレスが登録済みかを外部から総当たりで調べられる）
- ログイン試行にレート制限がかかる（IP 単位・アカウント単位）
- リフレッシュのたびにトークンがローテーションされる
- **失効済みトークンの再提示は盗用として扱い、そのユーザーの全トークンを失効させる**
- **ただし猶予時間（10秒）内の後継への参照は盗用としない**
  （タブを複数開いた利用者の同時リフレッシュを誤検知しないため。[技術スタック](tech-stack.md) 参照）
- ローテーションの「旧を失効 → 新を発行」が同一トランザクションで行われる

**判断が必要な点（実装時に決める）**

- ログアウト後も発行済みアクセストークンが最大15分間有効である旨を、利用者にどう伝えるか

### 1.3 プロフィール

- 表示: ハンドル / 表示名 / 自己紹介 / アバター / 投稿数 / フォロー数 / フォロワー数 / **都道府県制覇率**
- 編集: 表示名 / 自己紹介 / アバター
- 一覧: 投稿（投稿日順）と旅行履歴（訪問日順）を切り替えられる

### 1.4 パスワード変更

現在のパスワードの入力を必須とする。変更後は**そのユーザーの全リフレッシュトークンを失効させる**
（パスワードを変えた理由が漏洩の疑いである場合に、既存のセッションが残るのは意図に反するため）。

### 1.5 退会

物理削除ではなく、以下を行う（[ER図](er-diagram.md) の `users` 参照）。

1. `deleted_at` を設定する
2. メールアドレスを復元不能な値に置き換え、表示名を「退会したユーザー」、自己紹介とアバターを空にする
3. 投稿・コメント・いいね・フォロー・メディア（S3 のオブジェクトを含む）を削除する
4. ハンドルは解放せず保持する

**受け入れ条件**

- 退会後、そのユーザーのハンドルで新規登録できない
- 退会したユーザーが書いたコメントが残っている投稿を開いてもエラーにならない
- **S3 のオブジェクトが削除されている**（データベースの外部キー制約では消えないため、明示的に削除する）

## 2. 投稿

### 2.1 投稿の作成

| 項目 | 制約 |
|---|---|
| 画像 | 1〜4枚。**代替テキストは入力させない**（2026-08-29 に廃止。理由と代償は requirements.md） |
| 本文 | 1〜1000文字 |
| 都道府県 | **必須**。47件のマスタから選択（自由入力は不可） |
| スポット名 | 任意、100文字まで |
| タグ | 任意、5個まで。正規化（前後空白除去・NFKC・小文字化）して保存する |
| 訪問日 | **任意**（2026-08-29 に必須から変更）。未来日は不可。**省略した投稿は旅行履歴に出ない** — 並べる軸そのものが無いため |

**画像アップロードの流れ**

```
1. POST /media/presign   → media を pending で INSERT し、署名付き URL を返す
2. ブラウザ → S3        → 署名付き URL へ直接 PUT
3. S3 イベント → Lambda → 検証・EXIF除去・variants 生成 → status を processed へ
4. POST /posts          → media を投稿に紐づけて確定する
```

**受け入れ条件**

- 署名付き URL に **Content-Type と最大サイズが焼き込まれている**
- **EXIF の GPS 座標・撮影日時が除去されている**（変換後のオブジェクトを実際に検査して確認する）
- 拡張子や申告された Content-Type ではなく、**マジックバイトで形式を判定している**
- `processed` になっていないメディアを含む投稿は作成できない
- 手順2と4の間で中断した場合、`pending` のメディアが残り、**S3 のライフサイクルで期限削除される**
- 他人がアップロードしたメディアを自分の投稿に紐づけられない

### 2.2 投稿の編集・削除

- 編集できるのは本文・都道府県・スポット名・タグ・訪問日。**画像の差し替えは対象外**
- **自分の投稿のみ操作できることをサーバー側で検証する**（テストで担保する）
- 削除するとコメント・いいね・タグの紐づけ・メディアが連鎖削除され、S3 のオブジェクトも削除される

## 3. 反応

### 3.1 いいね

- 同じ投稿に二重にいいねできない（複合主キーで担保）
- **`posts.like_count` の増減を、いいねの登録・削除と同一トランザクションで行う**
- 自分の投稿へのいいねは可能とするが、**自分への通知は作らない**
- 取り消すと、対応する通知も削除される

### 3.2 コメント

- 1〜500文字、フラット1階層（返信ツリーは対象外）
- **`posts.comment_count` を同一トランザクションで増減する**
- 削除できるのは、コメントの作成者と**投稿の作成者**の両方
  （自分の投稿に付いた不快なコメントを消せないと、投稿ごと消すしかなくなるため）

---

## 4. フォロー

- 自分自身をフォローできない（DB の CHECK 制約で担保）
- 既にフォローしている相手への再フォローはエラーにせず、結果を同じにする（冪等）
- 解除すると、対応する通知も削除される

---

## 5. フィード

| 種類 | 内容 |
|---|---|
| フォロー中 | 自分がフォローしている利用者の投稿を投稿日順に表示する |
| 新着 | 全利用者の投稿を投稿日順に表示する |

**受け入れ条件**

- **カーソルページネーション**で取得する（`OFFSET` は使わない）
- **画面の下端に近づいたら自動で読み込む**（無限スクロール）。
  **明示的なボタンも残す** — 自動読み込みとボタンは排他ではなく、
  両方置けばスクロールで読む人もキーボードの人も失わない
- **新しい投稿は30秒ごとに確認し、帯で知らせるだけにする。**
  勝手に差し込むと、読んでいた位置が押し下げられる
- 20件の取得が **2〜3クエリで完結する**（投稿本体 → 関連する media / user / tag を IN 句で一括取得）
- いいね済みかどうかが1クエリで解決される（`WHERE user_id = ? AND post_id IN (...)`）
- 誰も投稿していない状態でも空のフィードとして正しく表示される

## 6. 発見

| 機能 | 内容 |
|---|---|
| 都道府県で絞り込み | 47件から選択。地方（関東など）でも括れる |
| タグで絞り込み | |
| キーワード検索 | 本文とスポット名を対象に全文検索する |
| ユーザー検索 | ハンドルと表示名を対象とする |
| 人気順 | 指定期間内のいいね数の多い順。**「期間」は投稿日で絞る**（「その期間に付いたいいねの数」ではない。後者は `likes` の期間集計になり、1画面ごとに全件を数えることになる） |

**受け入れ条件**

- **日本語のキーワードで検索できる**（ngram パーサを使う。既定のパーサでは日本語が一切ヒットしない）
- **空白で区切った語は「すべてを含む」で絞り込む（AND）。**
  MySQL の自然文モードは「どれかを含む」であり、語を足すほど結果が広がる。
  探すときに語を足すのは絞り込むためなので、意図と逆になる
- **1文字の語は検索に使えない。** ngram のトークン長が2であり索引に当たらない。
  黙って0件にせず、理由を伝えて断る
- **`+ - " ( ) *` などの記号は検索語の一部として扱う。** BOOLEAN MODE の
  演算子として解釈されると、「-東京」が「東京を含まない」になり意図と逆になる
- 絞り込みの軸（都道府県 / タグ / ユーザー / 訪問日の期間 / キーワード）を**組み合わせられる**
- 検索クエリの組み立てで、**ユーザー入力を SQL 文字列に連結していない**（必ずプレースホルダにバインドする）
- 該当0件のときにエラーではなく空の結果を返す

**判断が必要な点**

- 全文検索の索引が肥大した場合に OpenSearch へ差し替えるかは、負荷試験の実測後に決める
  （`PostSearcher` インターフェースの背後にあるため、差し替えても呼び出し側は変わらない）

## 7. 通知

| 種類 | 契機 |
|---|---|
| `like` | 自分の投稿にいいねされた |
| `comment` | 自分の投稿にコメントされた |
| `follow` | フォローされた |

**受け入れ条件**

- **通知の INSERT が、契機となる操作と同一トランザクションで行われる**
  （「いいねは記録されたが通知が消えた」状態を作らない）
- 自分の行為で自分に通知が来ない
- 未読件数が取得できる
- 個別および一括で既読にできる
- 契機が取り消された（いいね解除・フォロー解除・投稿削除）場合、対応する通知が消える

## 8. 都道府県制覇マップ

プロフィールに、投稿がある都道府県を塗り分けたマップと制覇率（n/47）を表示する。

### 地理的に正確な地図ではなく、タイルグリッドを自作する

47県を**同じ大きさのマス**として、地理的な位置関係がおおよそ分かるように並べる。
形状は再現しない。

**理由は3つある。**

1. **ライセンスの問題が構造的に消える。** 調査した結果、そのまま使える日本地図 SVG は
   GFDL（コピーレフト）のものしか見つからず、MIT のリポジトリに混ぜると
   ライセンス条件の説明が必要になる。パブリックドメインの地理データはあるが、
   シェープファイルからの変換工程を維持することになる。自作すればどちらも発生しない
2. **アクセシビリティの要件と噛み合う。** 実際の地図では香川・大阪・東京の
   タップ領域が数ピクセルしかなく、北海道との差が極端になる。
   **均一なマスなら全県が同じ操作しやすさになる**
3. **用途に対して形状の正確さが要らない。** 見たいのは「どこを制覇したか」であり、
   県境の正確な形ではない

**代償**: 「日本地図が塗られていく」という見た目の訴求は、実地図より弱くなる。

### 実装方針

- 配置（各県の行・列）は**データとして1ファイルに切り出す**。見た目の調整を
  コンポーネントを触らずに行えるようにする
- 地方区分（`prefectures.region`）で色相を分け、訪問済み／未訪問を明度で分ける

### 受け入れ条件

- **色の違いだけで情報を伝えていない。** 塗りのパターンと文字でも示し、
  同じ内容を表形式でも提供する
- 各マスが `aria-label`（県名と投稿件数）を持ち、**キーボードでフォーカスできる**
- マスから該当県の投稿一覧（`/prefectures/[code]`）へ遷移できる
- 投稿が0件でも表示される（全県が未訪問の状態）
- 画面幅が狭いときもグリッドが崩れない

## 9. 運用機能

| 機能 | 内容 |
|---|---|
| `GET /api/livez` | プロセスの生存のみ。依存先を見ない。**ロードバランサはこちらを見る** |
| `GET /api/readyz` | データベース疎通を含む。デプロイ時の投入判定に使う |
| 構造化ログ | JSON を標準出力へ。リクエスト ID を全ログに付与する |
| メトリクス | CloudWatch EMF 形式でログに埋め込む |

## 実装順序

1. **認証**（1.1〜1.2）— これが無いと他の機能を利用者ごとに検証できない
2. **投稿と画像**（2.1〜2.2）— 画像パイプラインが最も不確実性が高いため早めに通す
3. **反応とフォロー**（3・4）
4. **フィード**（5）— ここで初めて性能の議論ができる
5. **発見**（6）
6. **通知**（7）
7. **制覇マップ**（8）
8. **プロフィール周辺**（1.3〜1.5）
9. **AWS へのデプロイと負荷試験**
