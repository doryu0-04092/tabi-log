### apply して分かったこと（2026-08-31）

**H3 の対応のうち、Lambda の同時実行の予約は入れられなかった。**

```
InvalidParameterValueException: Specified ReservedConcurrentExecutions
for function decreases account's UnreservedConcurrentExecution
below its minimum value of [10]
```

このアカウントの Lambda 同時実行の上限は **10** である
（`aws lambda get-account-settings` で確認。新しいアカウントの初期値）。
AWS は「予約していない枠を 10 未満にできない」制約を持つため、
**上限 10 の環境では1つも予約できない。**

**予約しなくても歯止めは効いている。** 塞ぎたかったのは「Lambda が
際限なく増えて RDS の接続を食い潰す」ことであり、アカウントの上限が
そのまま同時実行の上限になる。

```
ECS     1 × 25 = 25
Lambda 10 ×  2 = 20   ← 予約ではなくアカウント上限が歯止め
合計           = 45 ≦ 85
```

**上限が引き上げられたら予約を戻すこと。** 1000 になった時点で
この歯止めは消え、接続の枯渇が現実的になる
（`infra/variables.tf` の `imageworker_max_concurrency` に書いてある）。

> **plan では分からなかった。** 予約の可否はアカウントの状態に依存し、
> 値の妥当性は apply の時点でしか判定されない。
> **「apply が通っても壊れている」の逆で、「plan が通っても apply で落ちる」型である。**

#### M10 — コメントの索引（直した）

`ix_comments_post` は `(post_id, created_at, id)` だった。一覧の問い合わせは
`WHERE post_id = ? AND id > ? ORDER BY id` なので、**post_id で絞ったあとの並びが
created_at → id になり、id の順を索引から得られない。**

実測（MySQL 8.4、コメント1万件）:

| 分布 | 結果 |
|---|---|
| 実態に近い（400投稿 × 25件） | `ix_comments_post` を使うが **Using filesort** |
| 1投稿に偏らせた（2000件） | 並べ替えは出ないが **key=PRIMARY / rows=4957 / filtered=20.17%** |

**最初は後者の分布で測り、「並べ替えが出ないので問題なし」と誤って判断した。**
索引を使わず id 順に走査して post_id を後から捨てる計画で、
他の投稿のコメントまで辿るため総量に比例して悪化する。
Extra だけを見ていると気づけない。

`(post_id, id)` に置き換えた（migration 000009）。`created_at` で並べる
問い合わせは1つも無いので3列目ごと落としている。
検証は `query_plan_test.go` に置き、**Extra だけでなく key も見る。**

#### H2 の処理時間 — 向き補正（推測は外れ、別の問題を直した）

「画素ごとの `At`/`Set` が 60 秒 timeout を超えうる」という推測は**外れ**だった。

実測（2026-09-01、向き6・転置あり）:

| 画素数 | 時間 | 割り当て |
|---|---|---|
| 1200万（4000×3000） | 188ms | 96MB / 1200万回 |
| 2400万（6000×4000） | 380ms | 192MB / 2400万回 |
| **5000万（上限）** | **886ms** | **400MB / 5000万回** |

時間は timeout 60 秒に対して十分速い。**問題は容量だった。**
`At` は返り値の `color.Color` を1画素ごとに箱に入れるため、
5000万回の割り当てと 200MB のごみが出る。Lambda は memory_size 1024MB で、
復号後の原本だけで 200MB を使う。そこへ出力の 200MB とごみ 200MB が乗る。

入力が `*image.RGBA` のときは `Pix` を直接読み書きする経路を足した。

| | 時間 | 割り当て |
|---|---|---|
| 変更前 | 886ms | 400MB / 5000万回 |
| **変更後** | **235ms** | **200MB / 2回** |

復号は `image.Decode` に任せており JPEG は `*image.YCbCr` を返すこともあるため、
**速い側だけを特別扱いし、それ以外は今までどおりの経路に落とす。**
2経路になったので、向き1〜8のすべてで両者が同じ結果を出すことをテストで固定した。

### H1. `originals/` のライフサイクル削除が確定済みの原本にも効く【照合済み・2026-08-31 修正済み】

`infra/s3.tf` のルール `expire-unconfirmed-originals` は、**名前に反して
`prefix = "originals/"` しか条件に持たない。**

```hcl
rule {
  id = "expire-unconfirmed-originals"
  filter { prefix = "originals/" }
  expiration { days = var.orphan_expiration_days }   # 既定 7 日
}
```

**投稿に使われた原本も 7 日で消える。** 残るのは JPEG q82・長辺 1080 の変換物だけで、
元に戻せない。

`docs/er-diagram.md` の「kind を増やせば別解像度を後から追加できる」と矛盾する。
`store/posts.go` は削除時に原本キーも対象にしており、**原本が残る前提で書かれている。**

#### 対応（案 A: 原本を残す）

**ライフサイクルの目的そのものは正しい。** 欠けていたのは
「確定したかどうか」の区別だけだったため、そこだけを足した。

S3 のライフサイクルは「タグが無いこと」を条件にできない。
そのため**確定していない側**に `state=pending` を付ける。

| 段階 | 変更 |
|---|---|
| アップロード | `PresignPut` が `state=pending` を**署名に焼き込む**。クライアントは `x-amz-tagging` を付けて送る |
| 投稿の確定 | `CreatePost` の成功後に `MarkKept` が `state=kept` へ変える |
| 期限削除 | `filter { and { prefix + tags } }` で pending のものだけ消す |

**タグを付ける役をクライアントにしたのは、そこが唯一「必ず通る」点だからである。**
Lambda に付けさせると、Lambda が失敗した原本にタグが付かず永久に残る。
掃除したいのはまさにその孤児である。

**付け忘れは起きない。** 署名にタグを含めたため、付けずに送ると S3 が拒否する。

| 変更したもの | 内容 |
|---|---|
| `infra/s3.tf` | ライフサイクルを `and { prefix + tags }` に。CORS に `x-amz-tagging` を許可 |
| `infra/iam.tf` | タスクロールに `s3:PutObjectTagging`（**署名付き PUT 自体にも要る**） |
| `backend/internal/storage` | 署名にタグを焼き込み。`MarkKept` を追加 |
| `backend/internal/store/media.go` | `ListOriginalKeys`（既存クエリの再利用。**DB が持つ実際の紐づけを正とする**） |
| `backend/internal/httpapi/posts.go` | 確定後に `markOriginalsKept` を呼ぶ |
| `frontend/src/lib/api/posts.ts` | PUT に `x-amz-tagging: state=pending` |
| `docker/localstack-init/` | ローカルのライフサイクルを AWS と同条件に |

**投稿は失敗させない。** 印が付かなくても投稿は成立しており、
ここで 500 を返すと「投稿はできているのにエラーが出る」形になる。
ただし黙って落とさず ERROR で残す。`keeporiginals_test.go` で両方を固定した。

> **未検証**: AWS 上で実際にタグが付くこと・署名が通ることは未確認。
> **アプライ後に確認する**（`deploy-verification.md` 1章）。

## 扱い方

**この一覧は「直すもの」ではなく「判断の材料」である。**

学習用の構成として意図的に割り切っている項目（L7・L9 など）と、
本番なら直すべき項目（H1・H4・M1）が混在している。
**一律に潰しにいくと、割り切りとして決めたことまで巻き戻すことになる。**

優先順位を付けるなら、次の順が妥当と考える。

1. **H1** — データが不可逆に失われる。しかも**設計書と矛盾している**
2. **H4・M1** — 秘密の露出経路
3. **L10** — 文書と実態のずれ。**放置すると他の判断の土台が狂う**
4. H2・H3・M3 — 動かしてみないと影響の大きさが確定しない
