# 進捗と残作業

最終更新: 2026-08-29

## 見た目の方向

**レトロポスター**（2026-08-29 に決定）。70年代の旅行ポスターを下敷きにしている。

| | |
|---|---|
| 紙 | `#f6ecd8` — 白ではなくクリーム |
| カード | `#fffaf0` |
| 墨（線・文字） | `#1c2b2d` |
| 主色 | `#ad3b1c` |

要点は3つ。**ぼかした影を使わない**（墨の輪郭＋ずらしたベタ影）／**角を落とす**（4px、丸ボタンは使わない）／**細い灰色の罫を使わない**（2px の墨の線）。

- `--color-page` と `--color-bg` を分けてある。**分けないとカードが地に沈む**
- ロゴだけ Bungee（ラテン専用・十数KB）を読む。**本文には使わない**
  （日本語のウェブフォントは数百KBで、見た目の差に対して代償が大きい）
- 主色は「塗りの上に文字」と「面の上の文字色」の両方で使うため、
  **いちばん暗い面（--color-surface）を基準に明度を決める**。
  `#d1502f`（4.28:1）→ `#b8401f`（4.39:1）→ `#ad3b1c`（4.87:1）と2回下げている

## 次にやること

**features.md の機能はすべて実装した。** 残っているのはインフラと性能である。

### 1. AWS へのデプロイ

**Terraform のコードは書いた**（`infra/`、2026-08-29）。
CI で `fmt` と `validate` を回している。**残っているのは適用である。**

```bash
cd infra
cp terraform.tfvars.example terraform.tfvars   # バケット名を自分の値にする
bash ../docker/build-imageworker.sh            # 無いと plan で落ちる
terraform init && terraform plan
```

**既定は動作確認のための最小構成**（0.25vCPU × 1タスク / db.t4g.micro、
月$45〜55 相当）。想定規模で測るときは `terraform.tfvars` で戻す
（`infra/README.md`）。

- **`plan` は通した**（74 to add / エラー・警告なし、2026-08-30）。
  データソース（マネージドプレフィックスリスト・キャッシュポリシー）は
  すべて解決した。**`apply` はしていない**
- apply だけでは動かない。イメージの push・マイグレーション・
  フロントエンドの配置が別に要る（`infra/README.md`）
- **データベースはプライベートサブネットにあり、手元から直接は届かない。**
  マイグレーションは ECS のタスクから流すか、踏み台を用意する

**書く過程で設計書の穴が2つ見つかった**（aws-architecture.md の冒頭に記載）:
Lambda から S3 への経路（ゲートウェイエンドポイントが必要）と、
Lambda から SSM への経路（環境変数で渡す判断にした）。

### 2. 本番相当での負荷試験

**仕組みは作ってあり、ローカルでは通している**（`perf/`）。
残っているのは **AWS 上で測り直すこと**である。

ローカルの実測（2026-08-29、50VU・4分・投稿2000件）:

    p95 = 7.9ms / エラー率 0% / 76,714リクエスト / 316 req/s

要件（p95 < 300ms）は満たしているが、**ローカルの数字は本番の予測にならない。**
本番は ECS Fargate 0.5vCPU×2 / RDS db.t4g.small であり、性能が違う。

AWS で測るときの観点:

- **フォロー中フィードが最初の対象。** 複数の利用者の投稿を1つの順序に混ぜる以上、
  索引1本では `Using temporary; Using filesort` を避けられない。
  厳しければ、フィードを事前に組み立てて持つ形（fan-out）へ作り方ごと変える判断になる
- **人気順に絞り込みを重ねると必ず並べ替えが入る。** 索引は
  「絞り込み1つ＋並び1つ」までしか同時に効かない
- **シードは段階的に投入**（2万 → 20万）し、各段階で測る
- **DB のレコード数と S3 の実データ量は切り離す** —
  20万件を額面どおり画像付きで作ると S3 だけで月$15前後の課金になる

## 作業の進め方（決まっていること）

| 項目 | 決定 |
|---|---|
| ブランチ | **既定ブランチへ直接コミットしない**（`guard-default-branch` フックが遮断する）。`git switch -c` してから作業する |
| マージ | **確認不要**（2026-08-28 に本人が許可）。ただし **CI が緑であることの確認は省略しない** |
| 生成物 | `docs/openapi.yaml` と `db/migrations` が正。`go generate ./...` と `npm run gen:api` で再生成し、CI が差分ゼロを検証する |
| 書式 | `.prettierrc` で明示。CI が `format:check` で検証する |
| lint | `golangci-lint run` を**手元で回してから push する**（CI で初めて気づくと往復が増える） |
| シェルスクリプト | 実行権限は `git update-index --chmod=+x` で明示的に記録する（Windows では `chmod` が反映されない） |

### この環境で繰り返し踏んだ罠

- **Git Bash はコマンドライン引数の日本語を壊す。** curl などへ日本語を渡すときは、
  ヒアドキュメントでファイルに書いてから `--data-binary @file` で送る
- **生成された構造体はフィールドがアルファベット順**。JSON から `"id"` を
  素朴に拾うと `author.id` を取ってしまう。取り出しは JSON として解析する
- **`zip` が入っていない。** Lambda のパッケージングは `cmd/lambdapack`（Go）で行う
- **カーソルを `id` にするなら、索引も `(絞り込みの列, id DESC)` にする。**
  `(user_id, created_at DESC)` は絞り込みには使えるが
  `ORDER BY id DESC` を解決できず `Using filesort` が出る。
  posts（000003）と notifications（000004）で同じ修正を2回した
- **E2E が増えると登録のレート制限に当たる。** 1回の実行で作る利用者は
  テスト数とほぼ同数で、失敗時の再試行でさらに増える。
  `.env.example` の `LOGIN_ATTEMPT_LIMIT` を引き上げる（本番は既定の 10）
- **楽観的更新のボタンは「押した」だけでは確定していない。**
  いいね・フォローは応答を待たずに見た目を変えるため、
  `aria-pressed` が変わっても送信中のことがある。画面を移る前に
  `waitForResponse` で待つ（`e2e/fixtures/app.ts` の toggleFollow / toggleLike）
- **`EXPLAIN` の `possible_keys` と `key` を取り違えない。**
  索引が「使われている」ことを確かめるつもりで候補一覧を見ていた。
  データが少ないうちは optimizer の選択が費用の誤差で決まるため、
  **`FORCE INDEX` で「その索引なら解決できるか」を見るほうが安定する**
- **先頭の列が同じ索引を2本持つと、並べ替えを解決できない側が選ばれる。**
  `(user_id, id DESC)` を足しても `(user_id, created_at DESC)` が残っていると、
  絞り込みの効き目は同じに見えるためオプティマイザが後者を選び、filesort が出る。
  **足すだけでなく、要らなくなった方を落とす**（000005 は落としており、
  000003 が落とし忘れていた）。落とせない場合（別の用途がある）は
  問い合わせ側で `FORCE INDEX` を書く。4か所で起きた
- **`go test` は既定でパッケージを並列に回す。** 同じデータベースを空にしてから
  使うテストが2つのパッケージにあると、互いのデータを消し合う。`-p 1` を付ける
- **テストを飛ばす条件を「CI かどうか」にしない。** CI にはデータベースを
  用意しないジョブもある。**用意した側が名乗る**形（`TEST_DB_REQUIRED`）にする
- **文章の中に「go:generate」「go:embed」と書くと指示行として解釈される。**
  staticcheck が SA9009 で落とす。かぎ括弧で囲む
